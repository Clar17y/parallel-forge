# Forge v0.2 upgrade contract

This is the required deployment procedure and compatibility boundary for the
v0.2 migration work in progress. It is not evidence that migrations or recovery
acceptance have passed. See [progress](v0.2-progress.md) and
[acceptance fixture A9](v0.2-acceptance-fixtures.md#a9--retained-v01-upgrade-and-gates).

## Deployment ordering

1. Stop admission of new work and request pause for existing runs. Let admitted
   effects settle; retain unresolved operation intents and their authority fences.
   Stop the old worker after it has drained. Do not infer that a separately
   dispatched command stopped merely because the worker process exited.
2. Stop the API and web controls for the migration window. Preserve a coordinated
   backup of the control PostgreSQL database, protected secret store, artifacts,
   managed-resource manifests and repository/worktree contents. Record the current
   schema revision and candidate identity without recording credentials.
3. Apply additive migrations with the new provisioned Python 3.14 environment.
   Existing policy snapshots, usage meaning, artifact bytes, approval bindings and
   operation receipts must remain unchanged. Legacy runs have no subscription
   profile by default; the absence of a new profile selects explicit legacy
   decoding, never conversion to a subscription route.
4. Start the new API and worker against the same control database and data root.
   Reconcile interrupted attempts and admitted effects before admitting successors.
   Verify that retained approval/execution/recovery states load and that unrelated
   managed worktrees remain usable. Start the matching web build.
5. Admit new v0.2 runs only after required route capabilities and the effective
   profile are verified and the existing human plan gate is satisfied. Profile
   defaults affect future runs; migration does not rewrite an approved envelope.

Do not run v0.1 and v0.2 workers concurrently against a database admitting v0.2
work. The API, worker and operator UI must come from the same supported release.
No rolling mixed-binary upgrade is claimed.

## Rollback limits

An additive schema does not imply that old binaries understand new run records.
Before any v0.2 run is admitted, downgrade is supported only if the actual migration
and retained-v0.1 fixture tests prove it. Once v0.2 records or effects exist, do
not drop their tables or run old workers against them. Stop admission, reconcile
or retain uncertain effects, and use a forward repair. Restoring a coordinated
backup requires a separate operator recovery decision that accounts for external
Git/provider effects since the backup; database restoration alone cannot undo
those effects. Never reset managed worktrees to manufacture rollback success.

Release evidence must name the migration revision, old/new binary candidates,
three retained v0.1 fixture states, before/after evidence digests, exact validation
commands and results, and any rollback case actually exercised. Until those
results exist, deployment compatibility and rollback remain unverified.

The current deterministic A9 harness covers the last v0.1 schema
(`20260909_0006`) using real records produced by the retained legacy services.
Plan approval, an unfinished developer with a completed write receipt, and
reviewed validation with pending pause/cancel have coordinated row/artifact
snapshots. It verifies original columns and artifact bytes after additive upgrade,
repeated head upgrade and recreated API/worker components. Unknown provider
completion stays in intervention; an existing tool receipt does not authorize a
replacement attempt. Existing authentication and version/evidence-bound controls
remain required after migration. See the progress record for exact checks and
hash-checked manifests.

This fixture downgrades an exclusively legacy, disposable test database to the
v0.1 boundary before taking its snapshot. It does not run the old binary, prove a
mixed-version deployment, restore a production backup, or authorize downgrade of
subscription records. The runtime guards for retained quota, probe, task-stop and
other v0.2 evidence remain unchanged.

## Subscription result evidence versions

New subscription results use schema 4 and retain the supervisor's exact typed
terminal launch proof. Successful decisions need a matching durable started
process identity, terminal receipt and worker identity; absent, legacy, uncertain
or conflicting launch evidence keeps settlement fenced. Interactive clients
closed after a validated final response record `completed`, separately from
cancellation. Process identity contains only the operating system creation
identity, not an authentication token. Protocol frames and stderr are excluded
from the proof.

Result schemas 1–3 retain their existing replay identity and usage accounting.
Replaying an old pending decision does not invent launch evidence or authorize a
new subscription plan gate. Such development-era pending results require forward
reconciliation; automatic recovery of them is not implemented or release-proven.
Legacy v0.1 plan approval evidence continues through its original decoder.

New primary reassignments use `BoundReassignDecision`, adding the exact stopped
source attempt and observed child version to the decision. The version-1 record
encoding retains its named record type; legacy `ReassignDecision` bytes remain
decodable and unsupported for new application. Accepted reassignment retains a
version-1 application receipt separately from the immutable provider result.
Recovery can replay that receipt after later attempts without changing the task
again. No schema migration or historical record rewrite is needed. This does not
make mixed old/new worker binaries safe.


## Candidate and acceptance evidence versions

Migration `20260911_0018` adds candidate-content and subscription-producer metadata
to evidence sets. Validation schema 2 retains a candidate tree digest; schema 1
retains its original canonical bytes. Subscription acceptance evidence has its own
kind and retains the actual primary, selection and optional reviewer attempts,
receipt proof and validation parent. A no-review selection keeps its reason and
contains no fabricated reviewer execution or approving report.

Content-bound controller checks use request payload protocol 2 and receipt schema
2; the outer durable operation envelope remains version 1. Receipts record the
candidate tree observed before and after the command. Each validation schema-2
member retains its exact controller receipt as an artifact parent. Publication
verifies those receipts again; a legacy HEAD-only receipt cannot establish a
content-bound result. Recovery reads the retained proof without launching another
command or treating the current worktree as proof of past execution. Cancellation
before launch retains a versioned no-effect receipt with no command result or
candidate observations; it does not count as a passed check.

Final acceptance dispatch retains a version-1 `run.subscription_validation_requested`
event binding the primary result/application, selected candidate, receipt proof,
plan approval and exact queued command. The command envelope remains version 1;
its closed payload adds `acceptance_attempt_id` alongside `semantic_attempt`.
Historical dispatch replay verifies that binding. Execution separately rechecks
current source authority and candidate contents, including after command execution
and publication. A retained event cannot replace those current checks.

Subscription PR and merge approval JSON use explicit schema version 2. They bind
the actual acceptance digest and candidate tree digest instead of a legacy review
digest. Their artifact descriptor envelopes remain version 1. Legacy approval
JSON retains its original fields and canonical bytes; decoders reject mixed
legacy/subscription fields and unsupported versions. The version-2 PR runner
document retains the actual command results and content-bound controller receipts.
The PR body retains the primary rationale and review selection, including the
actual no-review reason or reviewer handoff.

A version-1 `run.subscription_acceptance_decided` event binds the validation,
acceptance and frozen PR evidence to the source command and opens the existing
human PR gate. Human PR and merge approvals remain separate. Historical publication
recovery verifies retained sources and artifacts without re-running a model,
command or Git inspection as evidence of past execution. Current publication
preflight separately requires the clean managed candidate and matching contents.
The operator projection adds nullable acceptance and candidate-tree digests; both
approval screens verify these against the refreshed projection before requesting
an approval challenge. Production composition now supplies the shared final-acceptance
dispatcher to invocation and recovery workers. That wiring has local fake-provider
and PostgreSQL evidence; default official-client route admission remains disabled
pending capability verification. Whole release acceptance remains due, as tracked
in the progress log.

A legitimate failed final check records the separate version-1
`run.subscription_validation_rejected` event and a controller TaskHandoff. It
preserves the dispatched primary result/application bytes and records the actual
failed checks, validation digest and bounded repair decision. The budget debit,
primary requeue, candidate reopening and REMEDIATING transition are atomic;
exhaustion requires human intervention. Replays verify retained history without
another check or debit. A repaired candidate requires fresh primary selection,
acceptance and content-bound final validation before a new human PR gate.

PR-gate candidate drift and operator-requested revisions record the separate
version-1 `run.subscription_candidate_revision_requested` event. It binds the
actual frozen publication/acceptance, source command, candidate observation,
feedback digest, repair receipt and target. Current closed-primary authority is
required before reopening; retained acceptance history alone grants no new write
authority. The old acceptance bytes remain unchanged and the old PR gate is
invalidated atomically with the bounded primary requeue. Human revisions preserve
the automatic local-repair counter while still respecting cumulative task/run
budgets. Full bounded feedback is retained and delivered in the next primary's
untrusted context. Replay verifies the event, feedback and repair evidence without
another Git observation or debit.

Remote check/review failures retain the monitor's original bounded PR authority.
A separate version-1 `run.subscription_remote_repair_requested` event binds the
actual observation, published acceptance, source command and cumulative repair
receipt. It reopens the original primary without changing its accepted history
or local automatic-repair counter. The monitor alone increments the remote
counter. The handoff links the complete observation and includes at most 64 KiB
of untrusted remote context, explicitly identifying a truncated excerpt.

Fresh selection, acceptance and final checks are required before a revised push.
The subscription acceptance event has an explicit MONITORING_PR variant binding
the exact queued push and the original PR approval. Current preflight and
historical recovery rebuild its actual subscription source graph; a legacy
review event cannot stand in for this variant. Historical remote observations
are matched to their succeeded publication/update receipts, even after later
updates. Worker composition routes remote repair by the frozen execution mode;
missing subscription dependencies fail closed. Remaining paused controller paths
and final production dispatch remain pending.

Controlled subscription base updates reserve a cumulative repair in the separate
version-1 `run.subscription_base_update_admitted` event before an external effect.
The primary stays blocked and the candidate stays closed during the remote update
and local adoption. Their actual succeeded operation receipts are bound into
`run.subscription_base_adopted`, which requeues the same primary once and keeps
the run in REMEDIATING. The approved run/worktree baseline and previous acceptance
bytes remain unchanged; only the managed PR's current head/base advance.

The changed candidate requires fresh snapshot receipts, review selection,
acceptance and final checks. Its reviewed-push command includes both base-operation
IDs, checked against the current PR record and retained admission/adoption evidence.
The original human PR approval remains the publication authority; merge still
requires its own human gate. Subsequent remote failures and further base advances
retain the earlier accepted history. Expired committed base deliveries can be
acknowledged on resume without another debit. Partially effected deliveries first
require actual operation reconciliation, then retain their original authority
through resumed delivery. Exhausted budget stops before either base effect.

Run quiescence now includes subscription attempts, scheduled leases/effects and
client launch records. Expired or uncertain work still blocks resume and teardown;
queued tasks do not. A version-1 run-resume continuation can name the existing
subscription primary and frozen envelope without creating a legacy stage command.
Unstarted remote repair commands retain their original receipt-bound delivery;
a committed remote repair is acknowledged only after its exact history and expired
lease are proved, without repeating its repair debit.

For an interrupted, fully stopped attempt whose result was retained as stale,
resume re-proves its original contract, route, launch, usage and candidate epoch.
One bounded repair requeues that logical task. The original provider result stays
unchanged; its separate closed application receipt is referenced by the run-resume
event. Historical replay proves the debit and handoff without spending again.
Unsettled effects, altered sources and insufficient remaining budget leave the run
paused without partial changes. The candidate barrier is preserved. This path
does not authorize recovery of an uncertain client or an unapplied controller
decision merely because the run was paused.

Downgrade refuses any retained acceptance record or validation content binding.
With only version-1 evidence, the focused migration test preserves the existing
row and artifact bytes across downgrade to 0017 and upgrade to 0018. Full A9
release evidence still requires all three retained approval/execution/recovery
fixture states and their human gates; see the progress document for current scope.

## Shared provider quota state (0019)

Migration `20260912_0019` adds PostgreSQL quota pools, append-only exhaustion
observations and per-attempt admission records. API, workers and CLI must share
that database and the same `FORGE_SUBSCRIPTION_QUOTA_POLICY`. Forge does not read
the development framework's quota caches or invoke its provider skills.

The default identity groups models under each provider's `local` account and
auth/billing mode. Configure opaque account and pool labels when clients use
different accounts or providers expose distinct model pools. The optional JSON
policy supports `route_pools` selectors by provider, client, auth/billing mode
and optional model. See `.env.example`. Labels must not contain credentials,
email addresses or raw provider diagnostics. Mapping changes apply to future
admissions; a late result retains its original account/pool binding. Existing
pre-migration attempts have no such binding and do not fabricate one.

Known reset times remain distinct from the configurable probe cooldown
(`unknown_reset_cooldown_seconds`, default 3600, range 60–86400). At expiry a
blocked pool becomes eligible for one recovery attempt; this does not establish
remaining allowance. A probe abandoned during restart retains ownership until
the existing lease and client-stop evidence permit recovery. Newer exhaustion
evidence survives older responses. Skipping a blocked route reserves no attempt,
repair or execution capacity. Only an approved specialist fallback with matching
auth/billing boundaries may be selected; the selected primary stays unchanged.

Operators can inspect the task inspector, `GET /api/subscription-quota`, or
`forge subscription-quota list`. An audited report uses the authenticated,
idempotent `POST /api/subscription-quota/reports`, or the local operator CLI:

```text
forge subscription-quota report-exhaustion --provider anthropic --account local --pool weekly --reason "Confirmed weekly allowance exhausted" --idempotency-key quota-report-001 --reset-at 2026-09-13T01:00:00Z
```

The CLI lists one page at a time, defaulting to 100 pools. Use
`forge subscription-quota list --offset 100 --limit 100` for the next page.
Page size is 1–100 and offset is 0–1000000, matching the existing service bounds.

Use the actual future reset with an explicit timezone; omit `--reset-at` when
unknown. Reports cannot shorten an active block. Replaying the same request
does not extend it or create another audit event. Reports record server observation
time and a redacted reason, without an invented allowance balance.

Downgrade refuses retained exhaustion evidence or active probe/block state.
Do not clear production quota records to force a downgrade. The disposable
migration tests explicitly clean only their own test databases.

## Individual task stops (0020)

Migration `20260912_0020` adds `subscription_task_stops`. Each row refers to the
immutable API mutation/audit receipt, the exact attempt and lease generation,
stop and settlement task versions, settlement digest, and any causal resume or
superseding cancellation receipt. Original provider results and operator responses
remain unchanged as the stop lifecycle progresses.

Drain API and worker writes before upgrading, then run both processes on the
same schema. An active request remains requested after restart until the existing
launch, usage and effect evidence proves it stopped. A settled pause retains path
ownership but does not occupy execution capacity. Whole-run controls cannot clear
that individual pause. Resume rechecks authority, cumulative budgets and normal
quota eligibility; it never claims that allowance is available.

Downgrade refuses any retained task-stop row, including a completed, resumed or
superseded stop. Do not delete evidence to force rollback. Disposable PostgreSQL
migration coverage verifies this refusal; no production migration has been run.

## Worker registration diagnostics (0021)

Migration `20260912_0021` adds `subscription_worker_status`, containing only a
random worker-boot UUID, exact non-secret route pins, last report time and optional
terminal stop time. Upgrade the shared database before starting the new API and
worker binaries, following the drained deployment procedure above. Registration
reports use separate short transactions and do not grant runtime authority.

The worker publishes after recovery and renews every 15 seconds. At 45 seconds
without renewal, status becomes stale and current registration is unknown. A
reported stop remains terminal for that boot UUID; restart creates another UUID.
Unavailable reporting does not admit a route or spend an attempt/repair budget.
Missing reports, an empty current inventory and stale inventories are distinct.

Inspect Subscription profiles > Worker registration, follow the task-inspector
setup link, use authenticated `GET /api/subscription-runtime`, or run:

```text
forge subscription-runtime status --offset 0 --limit 25
```

Pages contain at most 100 worker reports and each report at most 64 route pins.
The response reports its observation time and whether another page exists. These
are worker construction registrations, not verified client version, sign-in,
model entitlement, billing/isolation conformance or remaining quota. Official
client verification and existing scheduler approval/quota checks still apply.

Rollback to 0020 drops only these diagnostic snapshots; it does not remove run,
quota, attempt or task-control evidence. Earlier rollback refusal guards remain
binding. Disposable PostgreSQL tests exercise upgrade, retained diagnostic rows,
downgrade and re-upgrade. No production database has been migrated in this work.

## Operator subscription installations

Set `FORGE_SUBSCRIPTION_INSTALLATIONS_PATH` to an absolute path shared by the API,
worker and operator CLI. The bounded UTF-8 JSON file has schema version 2 and at
most 32 installations. Each record selects only one built-in client discriminator,
an absolute executable, working directory and existing client home, exact
model/effort, an opaque account identity, SHA-256 executable identity, exact
official-client version, and opaque quota account/pool labels. Codex account
identity is also a SHA-256 digest and may additionally bind one provider limit ID
and bounded disabled MCP names; Claude may bind only its known allowance window
names. This development-only schema supersedes the unused version-1 shape; Forge
does not migrate version-1 files.

```json
{
  "version": 2,
  "installations": [
    {
      "client": "codex_app_server",
      "executable": "C:/absolute/path/to/codex.exe",
      "cwd": "C:/absolute/isolated/work",
      "home": "C:/existing/codex/home",
      "model": "gpt-6-astra",
      "effort": "low",
      "account": "<opaque-account-sha256>",
      "executable_digest": "<executable-sha256>",
      "client_version": "0.153.4",
      "quota": {"account": "personal", "pool": "weekly"},
      "quota_limit_id": "codex"
    }
  ]
}
```

The schema accepts no argv, environment, Python import, credential value or
capability boolean. Client launch scripts remain fixed in Forge, and `home`
references the operator-managed official-client directory in place; Forge does
not copy its credential cache. Missing, malformed, oversized, duplicate, changed
or digest-mismatched configuration loads no authority and does not prevent API or
worker startup. Exact manifest quota mappings are merged with
`FORGE_SUBSCRIPTION_QUOTA_POLICY`; a conflicting exact selector leaves the
installation unavailable.

The public worker composes Codex and Claude adapters only with Forge's durable
PostgreSQL/artifact evidence verifiers, and rechecks evidence on every invocation.
Configuration therefore cannot admit an official route by itself. Gemini remains
unregistered in production because issue #10 established no admissible verifier;
the closed loader supports its existing adapter only when a future code-owned
verifier dependency is supplied. Worker registration remains a construction
diagnostic, not evidence of sign-in, billing isolation or remaining allowance.

## Capability-evidence publication

Migration `20260920_0024` adds `capability_probe_diagnostics`, a current,
identity-digest-bound record of sanitized readiness failures and their expiry.
It stores no credential, configured path, provider output, or publication
authority. Repeated reports advance a per-identity revision; readiness may use a
current diagnostic to explain a blocked route but never to admit it. Downgrade
refuses to discard retained diagnostics. Do not delete production evidence to
force a rollback; disposable migration tests clear only their own rows before
rolling back to `20260916_0023`.

Claude's production launch environment is now distinct from providerless offline
conformance: it admits stored official `claude.ai` OAuth only through the selected
client home, never through inherited API/cloud/gateway credentials. This is an
environment correction, not published capability evidence. The bounded supported
auth-status metadata and any model turn remain separately authorized; neither
asserts provider-wide billing or usage-credit behavior, and this change performed
no live provider call.

`forge subscription-capabilities status` is offline and never contacts a provider.
It reports each Codex or Claude installation's executable state, eligible named
scopes, and current evidence where PostgreSQL/artifact storage is available.
`subscription-capabilities verify` runs the selected pinned client only against a
providerless Forge harness, retains a sanitized artifact, and reports the live
account/route proof classes still missing; it cannot publish authority.
Publication requires `--authorize-provider-contact`, `--client NAME`,
`--installation N` when selection would otherwise be ambiguous, and `--scope
NAME` when model/effort has more than one scope (for example `astra-primary` or
`astra-direct-repair`). A live probe binds the exact executable, home digest,
account digest, model, effort and scope; it never selects API keys, credits,
overages, or paid-route fallback. Codex uses the ChatGPT subscription route and
Claude uses stored `claude.ai` subscription OAuth. Neither has an API-credit or
paid fallback path. No live probe was run as part of this change.
