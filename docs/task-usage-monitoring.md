# Task usage checkpoint integration

Task usage observations, frozen baselines, totals, and checkpoints live in PostgreSQL. The API and worker construct these services from the same database factory. An observed provider attempt binds a durable work unit before launch, freezes the subject's baseline from that admitted source, and appends measured events. The worker evaluates run events and periodically reconciles requested or pausing checkpoints after restarts. Authoring workers also re-evaluate committed observations during live polling and between jobs, recovering a crossing when delivery was interrupted after its database commit. The live poll reads only the current attempt's latest event and advances a recovered checkpoint to pausing before cancellation; paused still requires process settlement. Owner commands go through authenticated API routes and persist a versioned receipt with an idempotency key.

New run and authoring subjects capture a monitoring admission snapshot in the subject-creation transaction: the current policy revision (including its absence), full configured route, and admission time. A delayed first provider launch samples history and policy as of that admission. Later project edits do not rewrite the frozen reference. The first source's effective route may differ from its configured route, but its configured route must match the admitted cohort. Older subjects without an admission row retain first-source policy/history selection; their original admission-time state cannot be reconstructed.

A run crossing requests one active checkpoint per subject. The checkpoint moves through `checkpoint_requested`, `pausing`, and `paused` only when the worker has proved process and effects settled. Terminal runs can record a late crossing without claiming a pause. A continuation retains the original baseline and either saves a next threshold above measured cumulative usage or disables further usage pauses for that generation's successors. An owner's monitoring override follows successor generations without rewriting the admitted baseline. Manual pause, cancellation, quota, and stale-input controls remain independent. Authoring recovery preserves recorded timeout, cancellation and quota failures; a monitoring crossing cannot turn them into a resumable usage pause. `stop` delegates actual cancellation to the normal run or authoring command and records the usage decision; a checkpoint row alone does not terminate a provider process.

The current product authorization grants operators access to all projects. GET checkpoint/report routes require an operator session; mutation routes require that session and CSRF protection. Command JSON has no actor field. The API binds the authenticated actor to the checkpoint's project and subject, compares the expected version, and rejects a repeated key with changed actor or payload. A stale policy revision returns HTTP409; the checkpoint panels refresh the policy so the owner can edit again. An uncertain response retains its original request body and key for exact retry. Measured totals come from the finalized source projection and unknown dimensions stay unknown.

Historical reports keep brainstorming, decomposition, and implementation in separate task categories. New authoring jobs use their admitted immutable job kind; older snapshots with no kind remain `authoring` and cannot be recategorized from later edits. Route filters use the durable configured/effective source bindings even when an interrupted source has only live telemetry. Such a subject is visible in its filtered cohort and excluded as incomplete; its live lower bound never becomes a measured historical sample. A current project policy edit changes the owner's current revision without rewriting earlier jobs' admitted revision or frozen estimate.

ADK model usage persists separate nullable completeness evidence for full input, output, and cached-input subset. `true` means the provider explicitly reported that dimension, including an explicit zero; `false` means the invocation lacked complete telemetry. Existing rows retain `null`, which is unknown rather than measured zero. Tool and control events do not count as model turns; an empty stream or an error/timeout before any model turn remains unknown. Multiple turns or output repairs are complete only when every contributing attempt proved the dimension. Positive counters from partial rows and prior live observations remain lower bounds without adding the overlapping live and final counters. The final-source sweep applies the same completeness projection after a worker restart.

Catalog cost estimates still use the numeric counters present for budget and settlement. Where provider token telemetry is incomplete, an estimate of zero or another amount is based on the observed numeric subset and does not prove actual provider spending; existing provider cost evidence and historic estimates remain unchanged. Changing unknown-cost admission policy requires a separate accounting decision.

The separate-process acceptance suite in `tests/acceptance/test_task_usage_monitoring_process.py` covers three distinct cases. One seeds a requested checkpoint and measured observation to prove restart settlement, authenticated reporting, CSRF rejection, and exact command replay. The other two use scripted providers behind production API/worker composition, with real supervised child processes and PostgreSQL. The authoring case emits 60/40 while its first process is live, pauses, continues, then settles a second 10/5 attempt as a saved proposal; the final report is 70/45. The delegated run uses an authenticated plan approval and actual worktree preparation, then observes a child 60/40 crossing, owner continuation, and another 60/40 child crossing. Its reports are exactly 62/42 and 122/82 because two primary attempts each reported 1/1. The two child attempts have different source/event identities; four normal attempts are charged in total and no repair debit is created by monitoring. Both generations retain the same frozen reference. This fixture explicitly allows two uncertain child attempts because scripted token telemetry is measured while provider cost and quota remain unknown; it does not relabel either unknown as zero. The seeded restart test alone must not be cited as provider-trigger proof.

For rollout, apply the current migration head `0041` before starting the matching API and worker processes. Monitoring storage and controls were introduced by `0038`–`0040`; `0041` adds retained authoring diagnostics. The authenticated owner can directly select `report_only`, `warn`, or `checkpoint`, change sampling settings, enter an explicit manual estimate, and set or clear optional caps. No calibration approval or mandatory note is required. A new policy affects new admissions; admitted work keeps its original policy and frozen reference.

For rollback, an owner can select `report_only` for new subjects and use normal controls to settle active work. Keep a database backup and use binaries compatible with the retained schema. Do not delete evidence to make a downgrade succeed. On a disposable populated PostgreSQL database, downgrade `0041 → 0039` refuses when removing observation/model telemetry metadata, admission snapshots, stop receipts, or checkpoint continuation state would discard evidence. Exact JSONB row snapshots, identities, values, timestamps, and the Alembic revision remain unchanged after refusal. Compatible rows survive a supported `0041 → 0039 → 0041` round trip. Retained `0041` authoring diagnostic events have their own refusal guard. These checks prove the named data shapes and targets; they do not authorize downgrading an active production database.

The browser preserves supported integer fields through exact decimal representations and emits numeric JSON tokens to the existing API. Existing numeric callers and server wire schemas remain compatible. Caps and monitoring history, minimum-sample, window, and manual-estimate fields are exercised at `9007199254740991`, `9007199254740992`, `9007199254740993`, and `9223372036854775807`. Values outside the supported range, fractional values, invalid negative/zero values, and already-rounded unsafe JavaScript numbers are refused. Blank and cleared optional caps remain null; model capacity does not seed a task cap. Generated client types and the reproducible generation check describe exact decimal values honestly. Owner changes retain optional notes, stale-save rebasing, uncertain-request replay, and append-only revisions.

The final local acceptance uses separate API, worker, web, and PostgreSQL processes. An authenticated Chromium journey through the production proxy saves advanced epic execution caps, clears them, rebases a stale cap edit, edits all six monitoring integer settings, and compares exact API payloads and PostgreSQL values. Profile creation and version appends save all four precision boundaries as numeric JSON tokens accepted by the strict API; a fifth version clears both caps while earlier immutable versions retain their exact values. Invalid nonfinite values cannot become an accidental cap clear when a pending request is copied. Three registered projects exercise selected and pooled report filters; unauthenticated requests return `401`, and an unregistered project UUID returns no rows. Forge currently grants the authenticated operator access to all registered projects; these checks do not invent a per-project tenant ACL. Reporting fixtures contain measured positive, measured zero, and unavailable sources. Provider execution is separately proved by supervised process journeys.

Checkpoint owner commands and monitoring-policy revisions also preserve signed-64-bit versions. Exact receipt comparisons accept valid older replay receipts and reject stale or mismatched responses. A fresh browser journey seeds high retained counters in disposable PostgreSQL, then performs actual run policy/continue and authoring policy/stop actions through the authenticated API; all four request/result pairs match durable receipts, including a result at `9223372036854775807`. The project editor saves a policy revision from maximum minus one to maximum and refuses another increment without sending a request. Incrementing beyond signed-64-bit storage is reported explicitly. High-version network-uncertain retry, stale refresh and next-checkpoint mode have focused component evidence; they are not claimed as additional browser journeys.

No-policy HTTP reporting remains usable and preserves missing usage as unknown.

A declared trusted-host `held-check` runs as an actual supervised subprocess in the managed worktree. Measured provider usage crosses while the check is held: the checkpoint remains requested or pausing, settlement is false, and owner continuation returns `409`. The check's PID and advancing heartbeat prove it remains active after the provider child has settled; its callback operation remains incomplete. Releasing the check permits actual exit, its durable successful operation receipt, and a settled pause. A separate leased-command injection checks the independent durable fence. A two-worker authoring test retains uncertainty across lease expiry and restart, refuses continuation while origin-host metadata is foreign, and pauses only after valid local proof and actual child exit. The foreign-host identity and lease injections are controlled host simulations; the held check and provider peers are actual local processes.

The final validation record links candidate hashes, current checks, matching retained evidence, failed receipts, and explicit limitations. The earlier broad backend run is historical and is not a final whole-backend pass. Native live-provider conformance, genuine execution on a second physical host, and real provider pricing remain unrun. Manually dispatched full hosted CI and merging need their own explicit authorization. Context-triggered pauses and progress-stall intervention remain separate follow-ups.
