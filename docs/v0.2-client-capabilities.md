# Forge v0.2 client capability matrix

Investigation began 10 September 2026 and was updated through 16 September.
Evidence includes official documentation, installed client schemas, metadata-only
account probes, providerless official-client isolation checks and one Antigravity
init-only observation. No live model turn or Forge-managed login was started;
Forge did not extract or copy credentials.

## Evidence classes

* **Docs** means an official vendor documentation claim.
* **Protocol/schema** means the installed client’s local interface or generated
  app-server schema. It proves the field exists, not that an account supports it.
* **Installed** means local executable version/help output.
* **Official offline** means the pinned official executable exchanged requests only
  with a bounded loopback fixture. It proves client-side transport and tool planning,
  not account, model-service or billing behavior.
* **Deterministic** means a Forge-supervised fake client exercised the implemented transport; it does not prove installed-client or account capabilities.
* **Live** is deliberately `unproven`: no model call or login was authorized.

## Trusted capability evidence contract — 14 September

Forge now represents trusted capability evidence as a closed, canonical manifest.
Its identity covers the exact provider and client version, executable digest,
digest of the canonical configured home, opaque account identity, model and
effort, specialist role, complete controlled-tool surface, and auth/billing modes.
The manifest references one verifier-sanitized artifact for each required proof
class: client identity, account authentication, route identity, billing
enforcement and tool isolation. Credentials, configured-home paths and raw
provider diagnostics have no field in the contract.

Migration 0022 adds an additive PostgreSQL evidence table and current-revision
indexes. The shared source serializes publication and invalidation per identity,
retains immutable revisions, and resolves only an unexpired current row whose
canonical manifest and referenced proof blobs still verify in the existing
artifact store. Exact replay is idempotent; changed replay, stale or replaced IDs,
identity mismatches, missing records and missing/corrupt artifacts reject.

The Codex, Claude and Gemini gateway verifier boundaries now receive the exact
invocation role/tool scope, may resolve evidence asynchronously, and must return a
report bound to that source-resolved identity. Their earlier capability booleans,
model assertions and quota telemetry remain necessary observations but no longer
establish admission by themselves. Deterministic fixtures create visibly fake
records only for offline tests; they do not enable the default production
registry.

Focused domain/PostgreSQL evidence tests and the complete gateway/agent suite pass
locally under Python 3.14. Provider-specific evidence producers, actual account
and billing conformance, installation loading and production registration remain
owned by issues #5–#11. No official client, account, model or billing operation ran
for this shared-contract change.

The fake-client suite and composed PostgreSQL cases pass; no model call or account

At that metadata-only stage this resolved the observed MCP configuration mismatch,

## Issue #5 allowance-only billing decision (14 September)

The selected personal ChatGPT route has no supported allowance-only billing
boundary. Issue #5 therefore completes through its explicit unsupported-product
branch: Forge retains the route as unavailable and does not create a production
billing verifier or billing-enforcement artifact.

The current [OpenAI pricing guide](https://learn.chatgpt.com/docs/pricing) and
[personal-plan credit guide](https://help.openai.com/en/articles/12642688-using-credits-for-flexible-usage-in-chatgpt-pluspro)
say that available credits continue eligible work after included limits. Turning
off automatic reload prevents that automatic purchase mechanism; it does not
disable an existing credit balance, and its maximum monthly spend applies only to
reload purchases. The personal guide also documents concurrent work taking a
credit balance below zero. A zero balance, unavailable purchases, disabled reload,
or a point-in-time usage percentage is therefore state, not an account policy that
prevents paid-credit consumption.

The admitted 0.153.4 configuration, `thread/start` and `turn/start` schemas expose
no credit, billing or spend policy. The installed official 0.154.0 client adds an
account-bound `ordinaryUsageAllowed` value to `account/rateLimits/read`, alongside
credit and optional spend-control observations. Its
[pinned response schema](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/app-server-protocol/schema/json/v2/GetAccountRateLimitsResponse.json)
describes current backend permission for ordinary included usage; it supplies no
per-turn enforcement. The 0.154.0 `thread/start` and
[`turn/start`](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/app-server-protocol/schema/json/v2/TurnStartParams.json)
schemas are byte-identical to the 0.153.4 copies and contain no billing selector,
reservation or fail-if-credit request. The public
[configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)
likewise has no credit, billing or spend setting. The read-only account snapshot
cannot make a later or concurrent turn allowance-only.

Forge consequently cannot truthfully produce the required `billing_enforcement`
proof or set `billing_allowance_enforced=True` for this account. The existing
gateway rejects a false or source-less billing claim before process launch, and
the ordinary production worker still registers no official subscription adapter.
Those fail-closed behaviors already have deterministic coverage; adding a fake
"successful" verifier would weaken the boundary, so no application or test code
changes are warranted.

There is no evidence lifetime to specify because no admissible proof is produced.
Reconsider this decision only if an official personal-account capability provides
either:

1. a service-enforced account policy that prevents paid-credit consumption across
   concurrent Codex surfaces; or
2. an account-bound atomic per-turn allowance-only request that the service rejects
   whenever included allowance is unavailable.

Any future implementation must bind that control to the opaque account, client
version and exact launch, expire it on account, policy, client or protocol change,
and add negative fake-client coverage before publishing trusted evidence. Merely
adding richer usage telemetry does not meet this threshold. The sanitized decision
record and retained source hashes are under
`.llm-output/root-issue-5-codex-billing/`; no client thread, model turn, login,
account/billing mutation or quota write was performed.

## Issue #6 official Codex isolation and verifier (14 September)

Forge now has a concrete production verifier and a bounded conformance harness for
the pinned official Codex 0.153.4 executable. The executable used for the retained
offline run has SHA-256
`444a3f0008050605cae73cd9b7a2dcac61294062dfaab56dd20430fd6498518b`.
The verifier recomputes that installation-specific digest, requires the unmodified
`app-server --stdio` entry point, and resolves only current source-verified evidence
for an exact supported account/home/version/model/effort/role/tool identity. Unknown
scopes, changed commands, changed executables, foreign verifier versions and
mismatched evidence remain unavailable before a client launch.

Admission and execution now share the same byte identity. On Linux, Forge copies
the digest-matched executable and model catalog into sealed descriptors and launches
or reads them through inherited `/proc/self/fd` paths. On Windows, Forge hashes held
file handles that deny write/delete sharing and retains those locks through process
settlement. Drift therefore fails before child execution, and the verifier version
is mechanically bound to both the isolation-policy and catalog digests.

The pinned built-in Astra and Sol catalog entries select code-mode-only tools and
multi-agent support; Astra also advertises model-owned clock and asynchronous
messaging tools. Feature flags alone therefore did not produce the closed surface.
Forge now ships a hash-pinned two-model policy catalog that retains the provider
model IDs but selects direct tools, disables shell, patch, search, node execution,
experimental tools and multi-agent behavior, and limits reasoning efforts to the
configured routes. Startup and per-thread configuration also remove prompt-injected
apps, collaboration, environment, permissions and skills instructions; disable
request-user-input, hooks, plugins, hosted search and inherited MCP servers; and
restrict direct dynamic tools to one `forge` namespace. Stable Responses-safe aliases
map back to the canonical Forge tool identity only after exact namespace, call,
thread and turn validation. Runtime account discovery hashes the returned ChatGPT
email and compares it to the selected opaque account identity before model discovery.

The official-client harness starts a fresh isolated home and repository, configures
MCP, hook and notification canaries, and sends `environments=[]` at both thread and
turn boundaries. Its loopback Responses fixture injects exact generic, custom,
native-local-shell, hosted-web, hosted-image and MCP call shapes, then one admitted
Forge read callback; it also invokes the disabled inherited MCP path directly. In
all five separately scoped runs, the outbound model request contained exactly the
single Forge namespace; unadvertised calls were returned as unsupported or only
echoed as inert response items, the direct MCP path was denied, no canary ran, no
credential header was sent, the Forge callback result round-tripped, and the
supervised process produced terminal stop proof. The scopes are Astra-low primary,
Astra-low direct repair, Sol-low planning/adversarial work, Sol-high correctness
verification and Sol-high security.

The 208-case Codex agent selection, 54 shared protocol cases and five composed
PostgreSQL scenarios pass locally under Python 3.14. The isolated model catalog is
present in the built wheel. Sanitized results and terminal process proofs for all
five official-offline scopes are retained at
`.llm-output/root-issue-6-codex-isolation/offline-conformance.json`; the artifact
contains neither credentials nor configured paths.

No result is published as trusted capability evidence. The loopback harness cannot
prove authenticated model behavior or allowance-only billing, and issue #5 proves
the selected personal ChatGPT account currently lacks the required billing control.
Accordingly `billing_enforcement` remains absent, every official Codex production
route stays unavailable, and no live provider call, login, account/billing change,
GitHub Actions run, PR action or merge occurred.

## Issue #10 supported-client correction and blocker — 16 September

Google's 18 June 2026
[migration announcement](https://github.com/google-gemini/gemini-cli/discussions/27274)
and [migration guide](https://antigravity.google/docs/cli/gcli-migration/)
make Antigravity CLI the supported command-line client for individual free, Pro
and Ultra access. The local Gemini CLI 0.59.0 sign-in path now refuses that use
and directs the operator to Antigravity. The issue #9 translation into the older
client is therefore historical configuration evidence, not a production route.
Installed `agy` 1.2.4 is the supported successor and the only current candidate.

An init-only, zero-turn probe selected a custom `forge-isolation-probe` agent with
`excludeDefaultComponents: true`, `inheritCustomizations: false`, command execution
off, and empty MCP-server, skill, plugin and tool lists. No prompt was submitted
and no provider turn, login or account/billing mutation began. Nevertheless, its
initialization event advertised 57 native tools, including `run_command`,
`write_to_file`, browser automation, web search, subagent management and generic
MCP access. The exact process tree was reaped and no `agy` process remained. This
matches upstream [isolation issue #1015](https://github.com/google-antigravity/antigravity-cli/issues/1015)
and fails issue #10's first criterion before any live conformance is permissible.

Forge now has a narrow fail-closed readiness gate for this prerequisite. It pins
the observed client version and executable digest, requires the intended agent,
empty declared and observed native-tool sets, and zero prompts/provider turns.
Any mismatch blocks conformance. Even a clean initialization would only make a
separately authorized live proof eligible to run; it cannot admit runtime by
itself. The protocol-compatible verifier returns no capabilities, the production
registry remains empty, and no trusted capability evidence was published.

Antigravity's [credit documentation](https://antigravity.google/docs/cli/credits)
describes `useG1Credits: false` as the prospective no-paid-credit setting, while
its [headless documentation](https://antigravity.google/docs/cli/headless/)
describes noninteractive operation. Neither control was exercised or accepted as
account-bound evidence because native-tool isolation already failed. The sanitized
diagnostic is retained in `.llm-output/issue-10-antigravity-blocker.json`; it is
explicitly not trusted runtime evidence. Issue #10 remains open and upstream-blocked.
