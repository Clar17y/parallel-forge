# Forge v0.3 stopped upgrade

This procedure extends the [v0.2 stopped-upgrade contract](v0.2-upgrade.md).
It is a supported **stopped** boundary: do not run old and new API/worker
binaries together against an admitting database.

1. Stop new admissions, request pause where appropriate, and reconcile known
   in-flight commands. Preserve unresolved effects and their authority fences.
   Stop the old worker, API, and web before migration.
2. Capture a coordinated PostgreSQL backup, artifact/data root, secret store,
   managed-resource manifests, and managed Git worktrees. Record old binary and
   schema revisions plus source/artifact hashes without credentials.
3. Apply additive migrations using Python 3.14. Keep old tasks, runs, profiles,
   approval bindings, artifacts, recovery rows, usage, and original bytes intact.
   New epic rows and verified handoffs preserve their frozen identities.
4. Start matching v0.3 API and worker binaries against the same database and
   data root. Reconcile uncertain commands and merge effects before successor
   admission. Verify old controls, current epic selections, budget ledger,
   child gates, and the operator UI before opening admissions.

Do not infer that a worker exit settled a remote or process effect. Repeating an
upgrade at head must be harmless. Downgrade through nonempty epic tables or
owner-edited budget/control state must refuse before losing data. Once v0.3
effects exist, use forward repair and explicit owner recovery; old binaries
are not claimed to understand new records. Restoring a database backup alone
cannot undo Git or provider effects. Do not reset managed worktrees to create a
clean rollback appearance.
