# Forge v0.2 release handoff

This is the personal-use v0.2 delivery summary for one operator on a local
Windows or Linux host. The integration baseline is `64e0187` on `forge/v0-2`,
including merged PRs #47–#56. The final release PR into `main` combines
[#28](https://github.com/Clar17y/parallel-forge/issues/28) (review and summary),
[#29](https://github.com/Clar17y/parallel-forge/issues/29) (authorized publication)
and [#30](https://github.com/Clar17y/parallel-forge/issues/30) (authorized merge).
That PR and #30 record the exact published head, checks and delivered revision.
Tagging, package publication and deployment are separate operations.

## Delivered behavior

- A selected primary can delegate bounded implementation, planning and review,
  or make a trivial repair directly when policy permits. PostgreSQL retains
  tasks, attempts, handoffs, ownership, budgets and approval evidence.
- Disjoint workers can share a managed worktree; conflicting paths queue.
  Independent worktrees can progress without a repository-wide execution lock.
- Profiles and routes are frozen for each run. Shared quota state, approved
  specialist fallback, process settlement and recovery preserve partial work
  and cumulative budgets without silently replacing the primary.
- The operator can inspect requested/effective routes and measured or unknown
  usage, pause/cancel/resume specialists and send bounded worker feedback.
  Multiple browser tabs reconcile against durable server state.
- The API and worker are separate processes. Repository effects remain subject
  to named tools, managed ownership, command policy and human plan/publication/
  merge gates.

## Accepted provider policy

`FORGE_SUBSCRIPTION_CLIENT_TRUST=operator` is the default for configured Codex,
Claude, legacy Gemini ACP and Antigravity clients. Existing client logins and
selected routes are trusted; optional capability publication is not a personal-use
release requirement. Readiness reports `operator_trusted` / **Ready to attempt**.
Antigravity always retains `approved_tools_unproved` because native tools may be
available. Its configured spending control remains `useG1Credits: false`.

Actual authentication/callback checks, route and role binding, credential filtering,
ownership, quota, budgets, bounded output, stop settlement and human gates remain
in force. Unknown usage or allowance is not a zero balance or a billing guarantee.
No paid-API fallback is introduced. Where configured, the routine alternative is
Codex subscription `gpt-6-luna` / medium; retained historical routes are unchanged.

## Local setup and first run

1. Use Python 3.14, Node 24, PostgreSQL 17, Git, Docker, uv and npm. For a new local
   instance, configure `FORGE_DATABASE_URL`, `FORGE_DATA_ROOT` and the loopback
   origins from `.env.example`. For existing data, follow the stopped-upgrade
   procedure below before starting new binaries or applying migrations.
2. Sign in through each chosen official client and create the closed
   [installation manifest](v0.2-upgrade.md#operator-subscription-installations).
   Give the API, worker and CLI the same absolute
   `FORGE_SUBSCRIPTION_INSTALLATIONS_PATH`. Keep provider credentials out of it.
3. Start the local PostgreSQL service, then use `npm run dev` for the supported
   development supervisor, or the separate process commands in the
   [operator runbook](operator-runbook.md#instance-and-startup). The supervisor
   installs frozen dependencies, migrates the configured database, builds the
   runner and rotates the operator session. Provider API keys are not needed for
   subscription startup. Use the manual commands to preserve an existing session.
4. Open the private bootstrap URL, register the repository and versioned project
   policy, then create/select an immutable subscription profile using
   [Subscription profiles or the local CLI](v0.2-profile-cli.md).
   Restart the worker after changing its installation configuration.
5. Inspect `forge subscription-runtime status --format text` and
   `forge subscription-quota list`. Resolve actual installation or route errors;
   **Ready to attempt** does not promise remaining allowance. Start a new task,
   inspect its plan and approve its bounded work. Use the
   [task inspector](v0.2-task-inspector.md) for attempts and controls. Publication
   and merge remain separate human decisions.

## Upgrade, recovery and support limits

Follow the [stopped-upgrade procedure](v0.2-upgrade.md): drain admitted work and
prove old writers stopped; stop operator mutations; preserve a coordinated
PostgreSQL, secret/artifact, manifest and worktree backup; migrate to
`20260920_0024`; start matching API/worker/UI versions and reconcile retained work.
Queued work is not proof of an active client. Uncertain effects retain their
authority fences until reconciled.

The rehearsals execute pinned v0.1 source in separate interpreters using a shared
dependency environment and scripted providers. They verify disposable dump
catalogs and filesystem archive bytes; they do not restore a backup or test a
historical installed distribution. Mixed-version writers and rolling upgrade are
unsupported. Downgrade is demonstrated only before subscription effects; retained
v0.2 evidence requires forward recovery, never deletion to force rollback.

Windows linked-quarantine rejection remains unverified where this session cannot
create directory symlinks. The actual fixture was prepared before the privilege
skip; this is not a passing Windows assertion. It does not weaken filesystem
protections or prevent configured operator-trusted CLI use.

One-run profile overrides and named per-task route selection are
[#31](https://github.com/Clar17y/parallel-forge/issues/31), explicitly post-v0.2.
Multi-user hosting, account/billing changes and new paid providers are outside this
personal-use release.

## Release review and checks

Primary source self-review reuses the retained scenario evidence and repaired
findings above. The release-preparation delta aligns package/API metadata to
`0.2.0` and corrects current setup/backlog guidance. Third-party dependency pins
and database migrations are unchanged. The historical test harness permits only
the bound first-party version and test-marker differences; dependency, interpreter,
source and checksum drift still fail.

The release-specific check record is [release validation](v0.2-release-validation.json).
It distinguishes fresh checks from reused evidence. No new provider campaign,
production migration or full Actions batch was run for this preparation.

Only **PR smoke** runs automatically for pull requests. Python/runtime, web,
browser and focused Docker workflows use manual dispatch and require their own
authorization. The final PR's current checks govern that candidate; development
PRs #47–#56 each passed their own smoke run.

The active `Main` ruleset requires a pull request, one approving GitHub review
and resolved review conversations, with stale approvals dismissed after a push.
Code-owner approval is required where applicable; no CODEOWNERS file exists at
the inspected `main` baseline. There are no configured bypass actors. The final
preflight must recheck these rules; primary self-review, a bot's thumbs-up and
publication authorization do not substitute for an approving GitHub review or
the user's immediate authorization for the exact merge.
