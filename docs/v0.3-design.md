# Forge v0.3 epic contract

Status: the deliverable for [issue #68](https://github.com/Clar17y/parallel-forge/issues/68), defining the implementation contract for issues #69–#78, based on `5adc944`. Issue #67 owns the separate readable plan-approval UI. This document fixes cross-lane identities, authority, and transitions; the named modules and API shapes below are proposed interfaces, not claims that v0.3 code exists yet.

## Boundary and invariants

An epic belongs to exactly one project. A human may save a brainstorming record, edit a brief, and adopt a brief revision and work-item graph before delivery. Each admitted work item creates one immutable existing `Task` source and one normal `Run` per attempt. Its planner starts with compact, frozen context, and its plan, PR, and merge require the same human approvals as any other run. Sequential admission means at most one unsettled child run per epic, even when several graph nodes are ready. Do not use the [subscription scheduler](../apps/orchestrator/src/forge/persistence/repositories/scheduling.py) for this: its logical tasks and dependency IDs are agent subtasks within a run.

The existing [task repository](../apps/orchestrator/src/forge/persistence/repositories/tasks.py) keeps task source immutable. [Run creation](../apps/orchestrator/src/forge/application/services/runs.py) binds task, current policy, repository base and configured profile and queues `start_planning` in one transaction. The [planner](../apps/orchestrator/src/forge/application/services/planning.py) reads task text, base, repository tree and instructions; the bridge must put relevant epic context in frozen task text or a validated, digest-bound planning-context extension. Do not rely on prior chat or mutate an existing task. Keep existing [run states](../apps/orchestrator/src/forge/domain/run.py), [approval evidence](../apps/orchestrator/src/forge/domain/approval.py), role permissions and provider adapters intact. Brief or graph adoption is never a run-gate approval.

PostgreSQL owns identities, versions, state, reservations, links, and receipt keys. Large bounded text and evidence may be content-addressed artifacts, with their descriptor/digest recorded in PostgreSQL; no authoritative in-memory fallback. API only authenticates, validates and commits commands/queries. The separate worker performs authoring and dispatch. Bound all new persisted text, treat it as untrusted, and validate new durable JSON with the existing [payload boundary](../apps/orchestrator/src/forge/domain/payload.py). Only an explicitly managed worktree receives repository writes.

## Frozen identities and snapshots

Use UUID identities and monotonic integer versions. `digest` means [canonical_digest](../apps/orchestrator/src/forge/domain/operation.py) of a closed, schema-versioned JSON object: sorted object keys, compact separators, UTF-8 SHA-256; array order remains significant. Include every declared optional key as JSON `null` when absent, never omit it. Sort unordered dependency/requirement ID arrays lexically and graph items by `(ordinal, item_id)` before hashing; preserve order only for explicitly ordered text/criteria. Store digest and schema version together and reject unknown versions. A revision is append-only. A selection pointer changes by compare-and-swap and does not rewrite the revision it selects.

| Record | Required identity and binding | Mutable part / invariant |
| --- | --- | --- |
| Epic | `epic_id`, `project_id`, `version` | Draft metadata and accepted pointers change with `expected_epic_version`; cross-project links fail. |
| Brief revision | `brief_revision_id`, `epic_id`, `revision_number`, `content_digest`, `source_job_id?` | Immutable problem, outcomes, scope/exclusions, decisions, assumptions and open questions. Requirements each have a stable `requirement_id`, bounded text and acceptance criteria. Adoption sets `accepted_brief_revision_id` on the epic. |
| Graph revision | `graph_revision_id`, `epic_id`, `brief_revision_id`, `revision_number`, `graph_digest` | Immutable bounded item snapshots and edges. Adoption requires the current accepted brief, validates acyclicity and atomically selects this graph. |
| Item snapshot | `item_id`, `graph_revision_id`, `ordinal`, `title`, `outcome`, `acceptance_criteria`, `dependency_item_ids`, `source_requirement_ids`, `item_digest` | `item_id` is stable inside a graph revision; an edited item is a new snapshot in a new revision. Sort ready items by `(ordinal, item_id)`. |
| Execution epoch | `execution_id`, `epic_id`, accepted brief/graph IDs and digests, `version`, aggregate limits | Snapshot fixed at start. Later edits remain drafts; they cannot alter active attempts or make an old success satisfy new criteria. Applying a revised graph to delivery requires an explicit new execution epoch after the current one settles. |
| Item attempt | `attempt_id`, `execution_id`, `item_id`, `attempt_number`, `context_digest`, `task_id?`, `run_id?`, `base_sha?`, `status`, `version` | Unique `(execution_id, item_id, attempt_number)` and unique non-null task/run binding. Replays use the same attempt; a retry has a new number, keeps earlier charges/evidence, and cannot coexist with an unsettled attempt. |
| Completion handoff | `handoff_id`, `attempt_id`, `run_id`, `run_version`, `merge_intent_id`, `merge_sha`, `integration_ref`, `verified_base_sha`, `evidence_digest` | Immutable proof produced only after settled merge and integration verification. Unique successful handoff per item in an execution epoch. |
| Authoring job | `job_id`, `epic_id`, `kind` (`brainstorm` or `decomposition`), input revision IDs/digests, `version`, state, reservation ID and result digest | Durable, subject-specific, read-only work before any delivery run. A result is a proposal; only version-aware operator adoption changes brief/graph selection. |

The graph includes all nodes and edges in its digest; reject duplicate IDs, cycles, self/cross-epic dependencies, oversized graphs and missing acceptance criteria. Validate every `source_requirement_id` against the accepted brief revision bound to that graph. Preserve requirement IDs across brief revisions for unchanged requirements; changed text/criteria creates a new revision and digest, so references never silently acquire new meaning. An accepted graph freezes its item criteria and dependency set. A graph edit after execution starts may be saved for review but does not hot-swap the active epoch. Deferred nodes remain visible and ineligible until a later accepted graph/epoch changes that decision.

## Cross-lane ports and API proposal

Implement these as Forge-owned typed application ports in new `application/ports/epic_*.py` modules. Signatures express required boundaries; concrete return types should be frozen as closed dataclasses/Pydantic records, not loose dictionaries.

```python
class EpicBriefPort(Protocol):
    async def accepted(self, epic_id: UUID) -> AcceptedBrief: ...

class EpicGraphPort(Protocol):
    async def accepted(self, epic_id: UUID) -> AcceptedGraph: ...
    async def snapshot(self, execution_id: UUID) -> FrozenGraph: ...

class EpicAuthoringPort(Protocol):
    async def submit(self, job: AuthoringJobSnapshot) -> AuthoringReceipt: ...
    async def observe(self, job_id: UUID) -> AuthoringOutcome: ...

class EpicBridgePort(Protocol):
    async def ensure_child(self, attempt_id: UUID, proof: EligibilityProof) -> ChildBinding: ...

class EpicEligibilityPort(Protocol):
    async def evaluate(self, execution_id: UUID) -> EligibilitySnapshot: ...

class EpicControlPort(Protocol):
    async def request_child_control(self, execution_id: UUID, run_id: UUID,
                                    action: Literal["pause", "cancel"],
                                    expected_run_version: int, key: str) -> ControlReceipt: ...
```

The returned/input records are closed and schema-versioned. `…_id` and `…_digest` refer to the identities above; these fields are the minimum shared fixture shape, with bounded prose represented by text or an artifact descriptor plus digest:

| Record | Essential fields |
| --- | --- |
| `AcceptedBrief` | `epic_id`, `project_id`, `epic_version`, `brief_revision_id`, `brief_digest`, requirements as `(requirement_id, text, acceptance_criteria[])`, decisions, assumptions, open questions. |
| `AcceptedGraph` | `epic_id`, `brief_revision_id`, `brief_digest`, `graph_revision_id`, `graph_digest`, item snapshots including `source_requirement_ids[]`, dependencies and ordinals. |
| `FrozenGraph` | `execution_id`, `execution_version`, accepted brief/graph IDs and digests, ordered item snapshots, aggregate budget ceiling reference. |
| `AuthoringJobSnapshot` | `job_id`, `epic_id`, `kind`, input brief/graph IDs and digests (nullable), `expected_epic_version`, bounded prompt/evidence descriptors, reservation ID. |
| `AuthoringReceipt` / `AuthoringOutcome` | Receipt: `job_id`, `job_version`, state, replay key. Outcome: same identity/version, result proposal digest/descriptor or safe failure category, measured usage or explicit unknown, settlement state. |
| `EligibilitySnapshot` | `execution_id`, `execution_version`, graph digest, ordered ready item IDs, per-item blocker codes, predecessor handoff digests and observed branch/base SHA. |
| `EligibilityProof` | `execution_id`, `execution_version`, `item_id`, `graph_digest`, sorted predecessor handoff digests, integration ref and observed base SHA, proof digest. |
| `ChildBinding` | `attempt_id`, `execution_id`, `item_id`, stage, `context_digest`, `task_id?`, `task_digest?`, `run_id?`, `run_base_sha?`; nullable IDs expose recoverable creation stages. |
| `ControlReceipt` | `execution_id`, `execution_version`, action/intent ID, `run_id?`, child command ID/status or pending settlement reason; absence is explicit null. |

`ensure_child` is idempotent across worker restarts and concurrent claims. Reserve attempt/budget and establish a unique binding before any provider work. It must call/reuse the ordinary run-creation transaction logic; if task creation and run binding cannot be one transaction, persist a stage and reconcile `reserved → task_created → run_created` by stable IDs/keys, never mint a new task/run on replay.

Admission transactions acquire locks in this order:

1. The epic row, then the current execution row; together they form the admission fence.
2. The item attempt, then the epic budget ledger/reservation.
3. The task, then the project when invoking ordinary run creation.

A unique active-attempt constraint backs the fence. Never acquire an epic/execution lock after holding an existing run lock. Collect run completion/control observations in a separate transaction without retaining its run lock, then acquire epic/execution locks and validate the observed run version, event/receipt identity and current epic authority before applying the observation.

Child-control intents follow these steps:

1. Persist the intent under the epic lock, then release the lock.
2. Invoke the existing run-control service.
3. Reconcile its receipt in a later epic transaction.

Callbacks cannot acquire these locks in reverse order. `EligibilityProof` expires on changed base/graph/control version or predecessor handoff.

Authoring jobs use a new subject-specific Forge interface with the **configured** route, quota, budget, process supervision and controlled read-only repository tools. Do not force a brainstorming/decomposition output into the existing [Planner `AgentGateway` result](../apps/orchestrator/src/forge/application/ports/agents.py), which is tied to a run plan. Preserve current runtime roles and adapters; no generic workflow platform, fake run, shell access, write/release tools, or new paid fallback. Job result, usage, timeout, cancellation, quota wait and late-result disposition are durable. Proposal adoption checks the input brief/graph digest and current version; stale output remains inspectable but cannot overwrite a later human edit or decide an open question. Decomposition must emit bounded outcomes, criteria, requirement references and a valid acyclic graph; child implementation plans are generated only by existing run planning after admission.

Proposed mutating HTTP routes use the existing operator session/CSRF boundary and `Idempotency-Key`, with `expected_epic_version` (or expected graph/job version as appropriate) in every body. Reusing a key with another payload conflicts; replay returns the original receipt after later state changes. GET projections return current version, accepted IDs/digests, proposal/draft distinction, ready/blocked reasons, active child link, gates and aggregate usage. Example route shapes:

| Action | Route | Version and effect |
| --- | --- | --- |
| Create/list/read epic | `POST /api/epics`, `GET /api/epics?project_id=…`, `GET /api/epics/{id}` | Project binding; idempotent create. |
| Save/adopt brief | `POST /api/epics/{id}/brief-revisions`, `POST /api/epics/{id}/brief-adoptions` | Append revision; adoption CAS selects its ID/digest, never authorizes a run. |
| Save/adopt graph | `POST /api/epics/{id}/graph-revisions`, `POST /api/epics/{id}/graph-adoptions` | Atomic graph validation; reject stale brief/graph references. |
| Authoring | `POST /api/epics/{id}/authoring-jobs`, `GET /api/epics/{id}/authoring-jobs/{job_id}`, `POST /api/epics/{id}/authoring-jobs/{job_id}/adoptions` | Durable submit/observe; version/digest-bound human adoption. |
| Execution and controls | `POST /api/epics/{id}/executions`, `POST /api/epics/{id}/executions/{execution_id}/commands` | Start/pause/resume/cancel with expected version and replay-safe receipt. |
| Progress | `GET /api/epics/{id}/executions/{execution_id}` | Item status, child run IDs, retained gates, reservations, evidence and blockers. |

These fixture bodies use illustrative IDs/digests; a real producer computes each digest from the canonical record. Send a distinct `Idempotency-Key` header with each POST. ## Execution transitions and money/usage

| Event | Atomic epic-side result | Child/effect settlement before next admission |
| --- | --- | --- |
| Start from accepted brief/graph | Freeze execution epoch, budget limits and deterministic graph order; `ACTIVE` with no child. | Eligibility and bridge admit first ready item. |
| Child plan/PR/merge gate | Remain `ACTIVE`, show current child and exact gate/evidence. | Wait for existing human approval; no epic command clears it. |
| Child merged and integration verified | Record immutable handoff and mark item satisfied once. | Recheck baseline and next ready item; `SUCCEEDED` only when all required items have proof and no unsettled effect. |
| Transient failure/retry | Retain attempt, receipt, usage and evidence; create a new attempt number only after old effect settles and policy permits. | Retry may not duplicate an existing task/run or erase a gate. |
| Pause | Under epic lock set `PAUSE_REQUESTED`, fence admission and persist idempotent child pause intent. | Send existing run pause command with current run version; settle command/process, then `PAUSED`. A pause at a non-pausable transition stays requested/blocked for reconciliation. |
| Resume | Versioned `PAUSED → ACTIVE` after settling prior intent. | Keep budgets, handoffs, run gate and run controls; use existing child resume rules where needed. |
| Cancel | Under epic lock set `CANCEL_REQUESTED`, fence admission and persist child cancel intent. | Send existing run cancel where legal; wait for command/effect settlement before `CANCELLED`. Existing merge-settlement refusal remains authoritative; report blocker and reconcile, never claim cancellation happened. |
| Permanent child failure or exhausted budget | Set `BLOCKED` with reason and preserve history; no successor admission. | Operator may resolve via explicit versioned action; no implicit budget reset. |
| Worker crash/late result | Reclaim lease and reconcile persisted intent, task/run binding, usage and merge proof. | Ignore stale authority; never equate worker exit with effect settlement. |

`ACTIVE`, `PAUSE_REQUESTED`, `PAUSED`, `CANCEL_REQUESTED`, `BLOCKED`, `SUCCEEDED`, `CANCELLED` are proposed execution states. A requested state is deliberately nonterminal. Existing child [run controls](../apps/orchestrator/src/forge/application/services/runs.py) use expected run version and have a merge-settlement cancellation refusal; epic controls must respect both. Use PostgreSQL row locks/version checks and durable intent/lease keys for pause versus admission, cancel versus task creation and concurrent dispatch. No API-side polling loop is authoritative.

The epic aggregate budget ledger belongs to the epic, not an execution epoch. It tracks at least tokens, cost in minor units, duration and retry count across all authoring jobs and every child attempt in every epoch; category and epoch IDs are dimensions for reporting, not reset boundaries. An epoch cap may narrow the remaining epic ceiling. Starting or resuming an epoch never clears prior consumption, unknown usage or unsettled reservations; raising an epic ceiling requires an explicit versioned, audited operator mutation. Reserve the maximum allowed next attempt **before** admission. Available = limit minus settled known consumption minus all outstanding reservations; `None`/unknown usage is never zero. On a settled result, replace its reservation with measured consumption. If telemetry is unknown or an effect remains unsettled, retain the reservation and block new admission if safe remaining capacity cannot be proven. Actual consumption above reservation is recorded honestly and blocks further work until an explicit versioned operator decision. A retry consumes a new reservation without refunding previous settled usage. Quota delay does not waive budget. Continue to use existing per-run/provider budget and quota admission; epic limits are an additional ceiling.

## Verification and compatibility

Use repository TDD for behavior: one focused failing test, smallest implementation, focused pass, then affected suite. Before the first push, test coupled transitions with PostgreSQL and providerless fixtures: concurrent duplicate start; pause versus eligibility/lease; cancel during task creation and during merge settlement; restart after reservation, task creation, run creation and handoff write; duplicate merge observations; stale graph/job adoption; predecessor merged but not integrated; branch advance before successor start; unknown usage, quota delay and retry. Assert exact task/run counts, preserved gates/reservations and no successor run in every blocked case. Add real Git ancestry checks and one supervised API/worker restart path; browser acceptance covers save/reopen, proposals versus adopted decisions, child gate links, pause/cancel and final proof. Use focused `python -m pytest ... -q` and affected web checks. Full CI and CI-triggering PR operations require authorization for that run under [AGENTS.md](../AGENTS.md).

Migration is additive: existing v0.1/v0.2 tasks, runs, approvals, provider envelopes, worktrees, artifacts and usage retain their bytes and meaning; standalone run creation needs no epic. New epic tables begin empty. Follow the stopped-upgrade and forward-repair boundary in the [v0.2 upgrade contract](v0.2-upgrade.md); do not claim old binaries can read new epic records or drop nonempty epic tables on rollback. Verify retained states and repeated upgrade on disposable data before release. A rollback after epic effects exist preserves records and requires reconciliation, not reset.

Deliberate v0.3 exclusions: parallel child-run admission within one epic; cross-project epics; automatic plan/PR/merge approval; generic workflow authoring; creating execution runs for brainstorming; changing runtime role/provider trust policy; retroactive satisfaction of revised requirements; and destructive cleanup of partial work. The operator can still use existing independent runs and existing in-run subscription delegation under their current rules.
