## Owner authority and soft controls

Workflow controls are defaults that help the owner make a decision. All plans
must provide a direct authenticated-owner override or an owner-editable setting
for approvals, readiness, sequencing, deferred work, limits, retries and review
requirements. An explicit owner action is sufficient authorization for the
operation it names. No additional permission, compulsory justification or
capability-proof workflow is required. An optional note may explain the choice.

Mutating commands expose `owner_override: false` by default and a nullable,
bounded `override_note` wherever they enforce a workflow blocker. The server
records the actor, action, affected IDs/versions, actual blocker codes and chosen
inputs. The same receipt is returned on replay. Overrides belong to the requested
action; a manual item launch does not approve its later plan, PR or merge. Those
gates have their own owner actions. The normal UI must offer these actions beside
the warning rather than require an unrelated administrative workflow.

Override records preserve facts. A dependency launched before verified
integration remains unverified; deferred work keeps its saved disposition;
unknown usage remains unknown and previous charges remain recorded. The owner
may raise or unset a configured ceiling, retry a quota-delayed route, launch a
blocked/deferred item, or acknowledge concurrent children. Real provider failure
and missing resources remain visible. The system never invents success, loses
an existing attempt or silently rewrites an immutable snapshot to justify the
decision.

| Default workflow check | Direct owner action | Facts retained |
| --- | --- | --- |
| Accepted-source selection | Launch an explicitly selected real saved brief/graph pair with an override. | Exact source IDs/digests and whether they were accepted. |
| Deferred item, unverified predecessor or another active child | Launch the selected item with an override. | Saved disposition, unresolved dependency evidence and concurrent child links. |
| Spending ceiling or unknown usage | Raise/unset the ceiling or acknowledge additional admission. | Earlier charges, unknown measurements, outstanding reservations and the override. |
| Retry or quota delay | Request another attempt or explicitly choose a configured route. | Prior failure, observed quota state and all earlier usage; the provider can still refuse the request. |
| Review/check or completion requirement | Accept the concrete gate or completion with its warnings. | Actual check results and a distinct owner-accepted basis; no invented passing evidence. |
| Paused or interrupted workflow | Request resume, cancellation or explicit recovery. | Actual process/remote-effect status, unresolved effects and the chosen recovery action. |

The automatic behavior and no-override examples below retain their conservative
defaults. References to workflow rejection, blocking, prerequisites or limits
describe that default, and every implementation must include the corresponding
owner path. Identity resolution and transaction consistency keep the recorded
action accurate. Saved resources and actual code baselines must exist. Choosing
a different saved source or recovering a stale edit is a new explicit action
with its own snapshot and receipt.

## Boundary and invariants

An epic belongs to exactly one project. A human may save a brainstorming record, edit a brief, and adopt a brief revision and work-item graph before delivery. Each admitted work item creates one immutable existing `Task` source and one normal `Run` per attempt. Its planner starts with compact, frozen context and uses the existing run gates and their owner actions. Default sequential admission permits one unsettled child run per epic; the owner can explicitly acknowledge concurrent manual launches. Do not use the [subscription scheduler](../apps/orchestrator/src/forge/persistence/repositories/scheduling.py) for this: its logical tasks and dependency IDs are agent subtasks within a run.

The existing [task repository](../apps/orchestrator/src/forge/persistence/repositories/tasks.py) keeps task source immutable. [Run creation](../apps/orchestrator/src/forge/application/services/runs.py) binds task, current policy, repository base and configured profile and queues `start_planning` in one transaction. The [planner](../apps/orchestrator/src/forge/application/services/planning.py) reads task text, base, repository tree and instructions; the bridge must put relevant epic context in frozen task text or a validated, digest-bound planning-context extension. Do not rely on prior chat or mutate an existing task. Keep existing [run states](../apps/orchestrator/src/forge/domain/run.py), [approval evidence](../apps/orchestrator/src/forge/domain/approval.py), role permissions and provider adapters intact. Brief or graph adoption is never a run-gate approval.

PostgreSQL owns identities, versions, state, reservations, links, and receipt keys. Large bounded text and evidence may be content-addressed artifacts, with their descriptor/digest recorded in PostgreSQL; no authoritative in-memory fallback. API only authenticates, validates and commits commands/queries. The separate worker performs authoring and dispatch. Bound all new persisted text, treat it as untrusted, and validate new durable JSON with the existing [payload boundary](../apps/orchestrator/src/forge/domain/payload.py). Only an explicitly managed worktree receives repository writes.

## Frozen identities and snapshots

Use UUID identities and monotonic integer versions. `digest` means [canonical_digest](../apps/orchestrator/src/forge/domain/operation.py) of a closed, schema-versioned JSON object: sorted object keys, compact separators, UTF-8 SHA-256; array order remains significant. Include every declared optional key as JSON `null` when absent, never omit it. Sort unordered dependency/requirement ID arrays lexically and graph items by `(ordinal, item_id)` before hashing; preserve order only for explicitly ordered text/criteria. Store digest and schema version together and reject unknown versions. A revision is append-only. A selection pointer changes by compare-and-swap and does not rewrite the revision it selects.

| Record | Required identity and binding | Mutable part / invariant |
| --- | --- | --- |
| Epic | `epic_id`, `project_id`, `version`, `accepted_brief_revision_id?`, `accepted_brief_digest?`, `accepted_graph_revision_id?`, `accepted_graph_digest?` | Draft metadata and accepted pointers change with `expected_epic_version`. Adopting a different accepted brief ID/digest atomically clears accepted graph selection (`accepted_graph_revision_id` and `accepted_graph_digest` become null) in the same expected-epic-version transaction; re-adopting the identical accepted brief preserves a still-matching graph (with ordinary replay semantics). Cross-project links fail. |
| Brief revision | `brief_revision_id`, `epic_id`, `revision_number`, `content_digest`, `source_job_id?` | Immutable problem, outcomes, scope/exclusions, decisions, assumptions and open questions. Requirements each have a stable `requirement_id`, bounded text and acceptance criteria. Adoption sets `accepted_brief_revision_id` and `accepted_brief_digest` on the epic (clearing accepted graph selection if the brief changed). |
| Graph revision | `graph_revision_id`, `epic_id`, `brief_revision_id`, `brief_digest`, `revision_number`, `graph_digest` | Immutable bounded item snapshots and edges. Graph adoption validates its bound brief ID AND digest against current accepted brief selection, validates acyclicity and required-on-deferred absence, and atomically selects this graph (`accepted_graph_revision_id`, `accepted_graph_digest`). |
| Item snapshot | `item_id`, `graph_revision_id`, `disposition` (`Literal["required", "deferred"]`), `ordinal`, `title`, `outcome`, `acceptance_criteria`, `dependency_item_ids`, `source_requirement_ids`, `item_digest` | `item_id` is stable inside a graph revision; an edited item or disposition change is a new snapshot in a new revision. Required `disposition` is part of immutable item and graph digests. Sort ready items by `(ordinal, item_id)`. |
| Execution epoch | `execution_id`, `epic_id`, selected brief/graph IDs and digests, `version`, aggregate limits | Snapshot fixed at start. Default start uses accepted selections; owner selection may use another real saved matching pair. Validate actual IDs/digests before any epoch, reservation, task or run side effect. Later edits remain drafts; older graph revisions remain inspectable; active execution frozen snapshots remain unchanged. Applying a revised graph uses a new epoch; default admission waits for the current epoch to settle, while an owner may acknowledge concurrent epochs. |
| Item attempt | `attempt_id`, `execution_id`, `item_id`, `attempt_number`, `context_digest`, `task_id?`, `run_id?`, `base_sha?`, `status`, `version` | Unique `(execution_id, item_id, attempt_number)` and unique non-null task/run binding. Replays use the same attempt; a retry has a new number and keeps earlier charges/evidence. Default admission waits for an unsettled attempt; an owner may acknowledge another distinct attempt while its predecessor remains unsettled. |
| Completion handoff | `handoff_id`, `attempt_id`, `run_id`, `run_version`, `merge_intent_id`, `merge_sha`, `integration_ref`, `verified_base_sha`, `evidence_digest` | Immutable proof produced only after settled merge and integration verification. Unique successful handoff per item in an execution epoch. |
| Authoring job | `job_id`, `epic_id`, `kind` (`brainstorm` or `decomposition`), input revision IDs/digests, `version`, state, reservation ID and result digest | Durable, subject-specific, read-only work before any delivery run. A result is a proposal; only version-aware operator adoption changes brief/graph selection. |

The graph includes all nodes and edges in its digest. IDs must resolve unambiguously to real records; duplicate IDs and cross-epic references cannot identify the requested source. Cycles, self-dependencies, graph-size recommendations, missing criteria and required-on-deferred dependencies produce default workflow warnings with an owner acknowledgement or editable limit. Manual ordering preserves actual edges. Validate every `source_requirement_id` against the brief revision bound to that graph. Each closed `ItemSnapshot` specifies an explicit `disposition`: `Literal["required", "deferred"]`, which is part of the immutable item and graph digests. Preserve requirement IDs across brief revisions for unchanged requirements; changed text/criteria creates a new revision and digest, so references never silently acquire new meaning. An accepted graph freezes its item criteria, dispositions, and dependency set. A graph edit after execution starts may be saved for review but does not hot-swap the active epoch. Deferred items remain visible and excluded from default dispatch; an owner may explicitly launch one while retaining its saved disposition. Unlaunched deferred work does not prevent `SUCCEEDED` once every required item has proof and all effects settle. Changing saved disposition creates a new graph revision and execution epoch.

## Cross-lane ports and API proposal

Implement these as Forge-owned typed application ports in new `application/ports/epic_*.py` modules. Signatures express required boundaries; concrete return types should be frozen as closed dataclasses/Pydantic records, not loose dictionaries.

```python
class EpicBriefPort(Protocol):
    async def accepted(self, epic_id: UUID) -> AcceptedBrief: ...

class EpicGraphPort(Protocol):
    async def accepted(self, epic_id: UUID) -> AcceptedGraph: ...
    async def snapshot(self, execution_id: UUID) -> FrozenGraph: ...

class EpicAuthoringPort(Protocol):
    async def submit(self, job: AuthoringJobSnapshot) -> AuthoringReceipt: ...
    async def observe(self, job_id: UUID) -> AuthoringOutcome: ...

class EpicBridgePort(Protocol):
    async def ensure_child(self, attempt_id: UUID, proof: EligibilityProof) -> ChildBinding: ...

class EpicEligibilityPort(Protocol):
    async def evaluate(self, execution_id: UUID) -> EligibilitySnapshot: ...

class EpicControlPort(Protocol):
    async def request_child_control(self, execution_id: UUID, run_id: UUID,
                                    action: Literal["pause", "resume", "cancel"],
                                    expected_run_version: int, key: str) -> ControlReceipt: ...
```

The returned/input records are closed and schema-versioned. `…_id` and `…_digest` refer to the identities above; these fields are the minimum shared fixture shape, with bounded prose represented by text or an artifact descriptor plus digest:

| Record | Essential fields |
| --- | --- |
| `AcceptedBrief` | `epic_id`, `project_id`, `epic_version`, `brief_revision_id`, `brief_digest`, requirements as `(requirement_id, text, acceptance_criteria[])`, decisions, assumptions, open questions. |
| `AcceptedGraph` | `epic_id`, `brief_revision_id`, `brief_digest`, `graph_revision_id`, `graph_digest`, item snapshots including `disposition`, `source_requirement_ids[]`, dependencies and ordinals. |
| `FrozenGraph` | `execution_id`, `execution_version`, accepted brief/graph IDs and digests, ordered item snapshots including `disposition`, aggregate budget ceiling reference. |
| `AuthoringJobSnapshot` | `job_id`, `epic_id`, `kind`, input brief/graph IDs and digests (nullable), `expected_epic_version`, bounded prompt/evidence descriptors, reservation ID. |
| `AuthoringReceipt` / `AuthoringOutcome` | Receipt: `job_id`, `job_version`, state, replay key. Outcome: same identity/version, result proposal digest/descriptor or safe failure category, measured usage or explicit unknown, settlement state. |
| `EligibilitySnapshot` | `execution_id`, `execution_version`, graph digest, ordered ready item IDs, per-item blocker codes, predecessor handoff digests and observed branch/base SHA (deferred items remain visible/ineligible and are excluded from ready IDs). |
| `EligibilityProof` | `execution_id`, `execution_version`, `item_id`, `graph_digest`, `disposition` (`"required"`), sorted predecessor handoff digests, integration ref and observed base SHA, proof digest. |
| `ChildBinding` | `attempt_id`, `execution_id`, `item_id`, stage, `context_digest`, `task_id?`, `task_digest?`, `run_id?`, `run_base_sha?`; nullable IDs expose recoverable creation stages. |
| `ControlReceipt` | `execution_id`, `execution_version`, action/intent ID, `action` (`Literal["pause", "resume", "cancel"]`), `run_id?`, child command ID/status or pending settlement reason; absence is explicit null. |

`ensure_child` is idempotent across worker restarts and concurrent claims. Reserve attempt/budget and establish a unique binding before any provider work. It must call/reuse the ordinary run-creation transaction logic; if task creation and run binding cannot be one transaction, persist a stage and reconcile `reserved → task_created → run_created` by stable IDs/keys, never mint a new task/run on replay.

Admission transactions acquire locks in this order:

1. The epic row, then the current execution row; together they form the admission fence.
2. The item attempt, then the epic budget ledger/reservation.
3. The task, then the project when invoking ordinary run creation.

Unique attempt identities and task/run bindings back the fence. Enforce sequential admission in the default application policy so an owner override can admit a distinct manual attempt without disabling transaction consistency. Never acquire an epic/execution lock after holding an existing run lock. Collect run completion/control observations in a separate transaction without retaining its run lock, then acquire epic/execution locks and validate the observed run version, event/receipt identity and current epic authority before applying the observation.

Child-control intents (pause, resume, cancel) follow these steps:

1. Persist an idempotent, version-bound intent under the epic lock, then release the lock.
2. Invoke the existing run-control service with `expected_run_version`.
3. Reconcile the command receipt and its control effects in a later epic transaction. Pause/cancel require process settlement; resume requires settled prior pause effects and an acknowledged child resume transition, not completion of the child's resumed work.

If an existing paused child needs resume, fence admission and keep the epic non-`ACTIVE` (`RESUME_REQUESTED`) until child resume is acknowledged/reconciled and prior pause effects settle. The resumed child preserves its prior approval gate, budgets, handoffs, and same run identity. If no child exists, resume reaches `ACTIVE` once prior pause effects settle. Refusal, stale run versions, retries, or worker crash recovery cannot leave an `ACTIVE` epic with a `PAUSED` child or silently authorize an approval gate. Callbacks cannot acquire these locks in reverse order. `EligibilityProof` expires on changed base/graph/control version or predecessor handoff.

Authoring jobs use a new subject-specific Forge interface with the **configured** route, quota, budget, process supervision and controlled read-only repository tools. Do not force a brainstorming/decomposition output into the existing [Planner `AgentGateway` result](../apps/orchestrator/src/forge/application/ports/agents.py), which is tied to a run plan. Preserve current runtime roles and adapters; no generic workflow platform, fake run, shell access, write/release tools, or new paid fallback. Job result, usage, timeout, cancellation, quota wait and late-result disposition are durable. Proposal adoption checks the input brief/graph digest and current version; stale output remains inspectable but cannot overwrite a later human edit or decide an open question. Decomposition must emit bounded outcomes, criteria, requirement references and a valid acyclic graph; child implementation plans are generated only by existing run planning after admission.

Proposed mutating HTTP routes use the existing operator session/CSRF boundary and `Idempotency-Key`, with `expected_epic_version` (or expected graph/job version as appropriate) in every body. Reusing a key with another payload conflicts; replay returns the original receipt after later state changes. GET projections return current version, accepted IDs/digests, proposal/draft distinction, ready/blocked reasons, active child link, gates and aggregate usage. Example route shapes:

## Execution transitions and money/usage

| Event | Atomic epic-side result | Child/effect settlement before next admission |
| --- | --- | --- |
| Start from saved brief/graph | Default to the accepted matching pair; an owner may select another real saved matching pair directly. Freeze the actual selected snapshots, budget limits, deterministic graph order and acknowledged warnings; `ACTIVE` with no child. Missing records and incorrect snapshot digests remain invalid inputs. | Default eligibility admits the first ready required item. An owner may explicitly launch a deferred or unverified item, retaining its saved disposition and actual dependency evidence. |
| Child plan/PR/merge gate | Remain `ACTIVE`, show current child and exact gate/evidence. | Wait for existing human approval; no epic command clears it. |
| Child merged and integration verified | Record immutable handoff and mark item satisfied once. | Recheck baseline and next ready required item; `SUCCEEDED` only when all required items have proof and all effects settle (deferred items do not prevent `SUCCEEDED`). |
| Transient failure/retry | Retain attempt, receipt, usage and evidence; create a new attempt number only after old effect settles and policy permits. | Retry may not duplicate an existing task/run or erase a gate. |
| Pause | Under epic lock set `PAUSE_REQUESTED`, fence admission and persist idempotent child pause intent. | Send existing run pause command with current run version; settle command/process, then `PAUSED`. A pause at a non-pausable transition stays requested/blocked for reconciliation. |
| Resume | Under epic lock set `RESUME_REQUESTED`, fence admission and persist idempotent version-bound child resume intent if a paused child exists (or verify prior pause effects settled if no child). | Send existing run resume command with `expected_run_version`; reconcile the acknowledged child resume transition and settled prior pause effects before `RESUME_REQUESTED → ACTIVE`. The child may then continue its ordinary work; resume settlement does not require the child run to complete. If no child exists, transition `RESUME_REQUESTED → ACTIVE` after prior effects settle. Retain existing gate, budgets, handoffs and same run identity. Refusal, stale version, retry or crash recovery keeps epic non-`ACTIVE` and never silently clears a gate. |
| Cancel | Under epic lock set `CANCEL_REQUESTED`, fence admission and persist child cancel intent. | Send existing run cancel where legal; wait for command/effect settlement before `CANCELLED`. Existing merge-settlement refusal remains authoritative; report blocker and reconcile, never claim cancellation happened. |
| Permanent child failure or exhausted budget | Default to `BLOCKED` with reason and preserve history. | The owner may retry, change the ceiling or acknowledge capacity uncertainty directly. Retain actual usage, outstanding reservations and failures; never reset them implicitly. |
| Worker crash/late result | Reclaim lease and reconcile persisted intent, task/run binding, usage and merge proof. | Ignore stale authority; never equate worker exit with effect settlement. |

`ACTIVE`, `PAUSE_REQUESTED`, `PAUSED`, `RESUME_REQUESTED`, `CANCEL_REQUESTED`, `BLOCKED`, `SUCCEEDED`, `CANCELLED` are proposed execution states. A requested state is deliberately nonterminal. Existing child [run controls](../apps/orchestrator/src/forge/application/services/runs.py) use expected run version and report merge-settlement cancellation refusal. Default resume waits for child acknowledgement and reconciliation. An owner may explicitly recover or admit further work despite unresolved effects; keep those effects visible and do not report a child as resumed, cancelled or settled without the corresponding observation. Use PostgreSQL row locks/version checks and durable intent/lease keys for pause versus admission, cancel versus task creation, resume settlement, and concurrent dispatch. No API-side polling loop is authoritative.

The epic aggregate budget ledger belongs to the epic, not an execution epoch. It tracks at least tokens, cost in minor units, duration and retry count across all authoring jobs and every child attempt in every epoch; category and epoch IDs are dimensions for reporting, not reset boundaries. An epoch cap may narrow the remaining epic ceiling. Starting or resuming an epoch never clears prior consumption, unknown usage or unsettled reservations; raising an epic ceiling uses an explicit versioned, audited owner action. Reserve the configured next attempt before admission. Available = limit minus settled known consumption minus all outstanding reservations; `None`/unknown usage is never zero. On a settled result, replace its reservation with measured consumption. If telemetry is unknown or an effect remains unsettled, retain the reservation and default to blocking new admission if remaining capacity cannot be proven. The owner can acknowledge that uncertainty and proceed directly; the projection retains the unknown amounts and warnings. Actual consumption above reservation is recorded honestly and defaults to blocking further work until an owner changes the ceiling or overrides that admission. A retry consumes a new reservation without refunding previous settled usage. Quota delays and epic limits are owner-overridable defaults; an override cannot make an unavailable provider deliver work or erase the delay evidence.

## Verification and compatibility

Use repository TDD for behavior: one focused failing test, smallest implementation, focused pass, then affected suite. Before the first push, test coupled transitions with PostgreSQL and providerless fixtures: concurrent duplicate start; pause versus eligibility/lease; cancel during task creation and during merge settlement; restart after reservation, task creation, run creation and handoff write; duplicate merge observations; stale graph/job adoption; predecessor merged but not integrated; branch advance before successor start; unknown usage, quota delay and retry. Assert exact task/run counts, preserved gates/reservations and no successor run in each default-blocked case. Pair workflow refusals with an explicit owner override, including combined warnings and an omitted optional note; assert that the requested operation proceeds once and preserves the actual facts. Add real Git ancestry checks and one supervised API/worker restart path; browser acceptance covers save/reopen, proposals versus adopted decisions, child gate links, pause/cancel and final proof.

Required acceptance test scenarios (as requirements and examples for future tests, not claims that production tests exist yet) must batch the following coupled behaviors:

- **Child pause and resume settlement**: pausing an epic while a child is at a plan/PR/merge approval gate fences admission and persists child pause; resuming that paused child transitions through `RESUME_REQUESTED`, fences admission, invokes child resume with `expected_run_version`, and reaches `ACTIVE` only after child resume is acknowledged/reconciled and prior pause effects settle, retaining the existing approval gate, budgets, handoffs, and same run identity; resuming an epic when no child is active transitions through `RESUME_REQUESTED → ACTIVE` once prior pause effects settle; resume command refusal, stale run version race, idempotent command replay, and worker restart during resume settlement keep the epic non-`ACTIVE` and never bypass child settlement or silently authorize a gate.
- **Brief and graph selection consistency**: adopting accepted brief B1 and graph G1, then adopting brief B2 atomically clears G1 selection (`accepted_graph_revision_id`/`accepted_graph_digest` become null); default execution start refuses an unaccepted selection before side effects, while an owner can directly launch an explicitly identified real saved matching pair. Incorrect digests, nonexistent records and cross-epic bindings create no side effects. Re-adopting the identical accepted brief preserves the matching accepted graph with standard replay semantics; an active execution's frozen snapshots remain unchanged by subsequent revisions while older revisions remain inspectable.
- **Immutable required and deferred disposition**: default dispatch reaches `SUCCEEDED` when all required items have verified handoffs and all effects settle, leaving deferred items visible and unexecuted. An owner can launch a deferred item directly while its frozen source still says `deferred`; the override creates exactly one attempt, task and run and never fabricates verification. Graph adoption defaults to refusing a required item that depends on a deferred item and exposes an owner acknowledgement for that policy warning. Cycle warnings retain the real edges and offer owner-directed manual ordering. Source identities must resolve to real records. Changing saved disposition creates a new revision; overriding a launch never rewrites the saved revision.

Use focused `python -m pytest ... -q` and affected web checks. Full CI and CI-triggering PR operations require authorization for that run under [AGENTS.md](../AGENTS.md).

Migration is additive: existing v0.1/v0.2 tasks, runs, approvals, provider envelopes, worktrees, artifacts and usage retain their bytes and meaning; standalone run creation needs no epic.
