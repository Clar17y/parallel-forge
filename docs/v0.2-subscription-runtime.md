# Forge v0.2: subscription-backed multi-provider agent runtime

## Outcome
An operator can run a strong primary orchestrator and specialist workers through authenticated official Codex, Claude and Google coding clients using an existing subscription. Forge schedules their work durably, enforces project policy and human gates, and shows which provider/mode executed each attempt. API-key mode remains explicit. Login/quota failure never silently enables paid usage or substitutes an unapproved model/provider.

The product target is the working standard of the local multi-provider framework
used to build Forge: a user-selected primary orchestrator with specialist workers,
bounded delegation, independent review when useful, and evidence-backed acceptance.
Connecting three clients alone does not satisfy v0.2. This is an operational and
capability target; identical answer quality cannot be guaranteed across clients or
model versions and must be assessed on representative coding tasks.

Product decisions below were confirmed with the operator after review of commit
`6d87fe0` on 10 September 2026. This is the implementation plan, not evidence of
implemented subscription support. Product choices are settled; official-client
feasibility and exact model mappings remain explicit delivery gates. On
16 September 2026 the operator explicitly approved issue #9's Gemini mapping:
the official runtime carries model `gemini-3.8-flash` and effort `medium`
separately. Installed-client conformance remains an issue #10 gate.

## Primary workload and durable delegation

The primary is an LLM role, not another name for Forge's deterministic state
machine. It proposes scope, assignments, review selection and acceptance within
approved policy. Forge remains authoritative for lifecycle transitions, tool
permissions, budgets and the plan/PR/merge human gates. Primary acceptance never
substitutes for human approval.

New subscription plan proposals include explicit canonical `owned_paths`, separate
from descriptive `affected_components`. The paths and exact policy command names
are part of the approved plan bytes. After human approval and worktree preparation,
Forge installs those paths and named checks into the primary's logical contract
without resetting identity, route or cumulative budget. An explicit empty path list
grants no writable paths. Retained legacy plan bytes remain unchanged; never infer
new path authority from legacy component prose. The primary's logical authority
must not become a reservation that prevents coordination while children are active;
actual mutations still require exclusive authority for their affected resources.

Scheduler admission derives the primary role from its persisted logical contract.
Its thinking lease does not reserve child paths, but still consumes configured
execution capacity. Primary mutations conservatively acquire a durable exclusive
worktree effect fence after active child writers drain. The fence lasts through
effect settlement or recovery, not the whole provider turn. Plain repository reads
are exempt only when the operation binding matches the exact persisted attempt
and lease. Snapshot capture, commits, named checks and unknown effects remain
exclusive. Pending legacy primary effects also fence new writers unless proven
to be bound reads. Separate managed worktrees remain independently schedulable.

A scoped plan naming an unregistered policy command is a rejected proposal.
After proving its current source, stopped launch and settled usage, Forge records
the rejection and spends at most one bounded repair debit to requeue the primary.
Exhausted tasks become terminal. Original provider result bytes remain unchanged;
an exact application receipt makes recovery replayable without a second debit.
Stale policy, changed source, cancellation and unsettled effects defer application
without consuming repair budget. A corrected proposal still requires the existing
human plan approval gate.

- Workers own full bounded outcomes, including their failing checks, routine
  repairs and self-review. Mechanical integration can belong to an integration
  worker; the primary owns integration decisions and final acceptance.
- The primary may make small, understood changes when delegation would add more
  work. It does not routinely duplicate worker investigation or validation.
- Forge handles scheduling, waiting, control delivery and pre-approved fallback.
  The primary yields after submitting structured decisions and releases execution
  capacity while waiting. Child work must not require an occupied parent slot.
- Workers return compact handoffs with links to detailed evidence. Wake the
  primary for decision-relevant completions, requested scope changes, unavailable
  prerequisites or exhausted repair limits, not routine polling or raw logs.
  Handoffs include changed paths, candidate identity, actual check results and
  residual concerns; summaries alone never establish successful validation.
- A worker's completed handoff retains ordered named-check history, including an
  ordinary failure followed by a successful repair in the same provider attempt.
  Each operation has a distinct receipt. Verify chronological order, terminal
  command evidence and stable historical snapshots; only the latest successful
  check for each name establishes validation of the final snapshot. Cancelled,
  timed-out, truncated or unverified checks cannot establish that proof. Expose
  exact command duration and bounded redacted output to the owning worker.
  New subscription command receipts use version 3; historical versions retain
  their original replay payloads. Within-attempt check repair sequences and
  scheduled repair debits are distinct measurements.
- Independent tasks continue when a sibling fails; dependent tasks wait. A worker
  may continue independent work while requesting a scope change. Whole-run stops
  are reserved for run-wide failures, operator controls or mandatory policy.

Persist a logical delegation task separately from provider attempts. Its contract
contains parent/run identity, purpose, dependency IDs, owned paths, typed acceptance
criteria, named validation commands, context/evidence references, route binding,
budget and repair limits. Contracts are structured task context, not interpolated
untrusted text in the trusted system-instruction channel. Validate dependencies
as acyclic, within the run and within the parent's authority.

Tasks need queued, running, blocked, reconciling and terminal states, plus durable
pause/cancel intent. Store handoffs, findings and the primary's acceptance or
reassignment decisions. Each new invocation receives a fresh attempt identity;
the logical task and aggregate budget survive retries and fallback. Scheduling
replay must not create duplicate child tasks. Keep specialist purpose separate
from tool capabilities; a role label never grants arbitrary tools.

New primary reassignment records bind the stopped child attempt and observed task
version. Apply them through the same durable decision/recovery transaction, only
after proving stopped client/operation history, unchanged ownership and candidate,
and the frozen specialist route with matching authentication/billing boundaries.
Retain the original requested route, files, contract, cumulative usage and repair
counts. Queue the same child and yield the primary; its child completion or scope
request wakes the coordinator. Reassignment itself reserves no provider attempt;
normal quota, capacity and remaining-budget admission still applies. Replay checks
an immutable application receipt even after subsequent child attempts. Old unbound
records remain readable without granting new authority. A primary cannot use this
decision to clear operator pause/cancel intent or revive an uncertain process.

An `accept` decision names its subject with `task_id`. Targeting an owned child
acknowledges its completed, verified handoff, copying that handoff's candidate and
complete receipt claims. Retain the accepting primary attempt and accepted handoff
attempt so later invocations can distinguish historical acceptance from newer work.
This returns control to the primary without advancing the run or changing the
candidate barrier. Targeting the primary's own task proposes final acceptance of
the integrated candidate, requiring current closed-candidate evidence, the selected
review outcome (or explicit policy-permitted no-review choice), final validation
and the existing human gates. Historical child acceptance never certifies the
current integrated tree.

Only the primary creates workers in v0.2. A reviewer has a task-lineage link for
audit but a fresh provider conversation, no inherited writer conversation and
read-only tools. Do not confuse lineage with provider-session inheritance; the
current reviewer `parent_execution_id` restriction must retain that independence.
Each invocation binds its own instructions, context, model/effort and permitted
tools, including continuation after recovery or delegation to a different provider.

## Worktrees, concurrency and candidate integrity

The unit of worktree delegation is the orchestrator/run. All its workers share
that managed worktree. There is one active orchestrator per worktree; additional
tabs observe or steer the same run. Separate runs use separate managed worktrees.
Do not create a worktree per worker by default.

- Ownership keys include canonical managed-worktree identity and normalized path.
  Enforce descendant overlap, Windows case rules and existing link/path defenses.
  The same relative path in another worktree is not an ownership conflict.
- Enforce reservations durably and at tool admission, not just in prompts. Queue
  known conflicts; scope expansion requires the primary's decision. The primary's
  own small edits follow the same reservation rules as worker writes.
- A stopped worker's scope request releases its execution slot and wakes its
  primary, including a primary already waiting on that child. It does not grant
  paths. Supply the exact request attempt and paths as untrusted invocation
  context. A response must bind to that request, preserve task identity and budget,
  and stay within the primary's approved scope; new authority outside that scope
  requires renewed approval. Resume a granted child through normal reservation
  checks so an active sibling keeps its ownership.
  Bound responses prove both stopped producers and the exact pending request.
  Grant/deny paths partition the request; only owned paths change in the child
  contract. Denial also queues the child with an explanatory historical response.
  A durable application receipt preserves both provider results and makes replay
  independent of later child progress. A new response cannot answer an old request
  after the child has resumed or requested scope again.
- No repository-wide lock or agent limit lasts for an attempt, command or run.
  Brief synchronization for a particular shared Git metadata/ref operation is
  allowed. A blocked or uncertain run in worktree A must not fence worktree B.
  Preserve registration and managed-root defenses while narrowing lock scope.
  Approved disjoint file effects retry only an explicitly contended worktree
  mutation lock, for at most five seconds before admission. Release all handles
  between attempts and revalidate the complete capability. Safety denials,
  admitted effects and release validation are never retried by this mechanism.
- Start with three active workers per run, configurable. Apply configurable
  host/provider capacity limits fairly across runs, without a repository-wide
  concurrency cap. Waiting parents and queued tasks do not consume active slots.
  The authenticated task snapshot shows observed host, frozen run and selected
  provider slot counts/limits, plus capacity constraints on queued tasks. It uses
  the scheduler's existing stopped-pause proof: confirmed stopped pauses release
  slots, while unconfirmed stops still count. Show the actual fair ordering
  (least recently served run, then oldest task), not a promised queue position.
  These read-only observations do not reserve launches or imply quota, ownership,
  approval or route eligibility. Missing observations remain unknown.
- A designated integration worker commits coherent checkpoints after the relevant
  writers settle. The existing commit tool stages the entire worktree: until its
  semantics are changed, this requires a worktree-wide checkpoint barrier that
  drains all admitted mutations and prevents new ones through commit completion.
  Never let workers accidentally commit siblings' unfinished changes.
- The primary may checkpoint its own approved small change through that same
  controlled commit tool and worktree barrier. Its operation uses a distinct
  authority codec that binds Forge-derived approved paths to both preparation
  and publication; the provider still supplies only a commit message. Reject
  foreign edits before staging and validate the exact prepared tree again.
  Historical integration and legacy commit codecs keep their original meaning.
  Recovery uses the retained attempt, paths and two-phase receipts without a
  live lease or another commit. Invalid lineage or a downgraded primary codec
  requires intervention and preserves the existing fence. Planning and closed
  candidates remain read-only; human publication and merge gates still apply.
- A worker's handoff snapshot is a read with a durable worktree freeze. Its exact
  tool/argument digest, attempt and lease must establish that read authority.
  Disjoint live writers may remain admitted while idle; every pending or uncertain
  effect must settle before capture, and reconciling writers still block it.
  The snapshot's exclusive effect prevents new mutations until its receipt is
  settled, including across restart. This exception does not apply to checks,
  commits, unbound reads or stale attempts. Owned-path handoff verification compares
  only that worker's changes while retaining the full historical snapshot.
- Authoritative validation and review use a stable candidate. For the initial
  shared-worktree design, a barrier prevents source changes during those checks
  and review; it affects only that worktree. Freeze/read the same candidate for
  repository reads and diff evidence. Reopen edits explicitly for remediation.
- Named commands may write outside a worker's file scope, including generated
  files or shared test data. Do not treat commands as read-only because they are
  called tests. Use conservative worktree-exclusive execution until trusted policy
  declares and enforces narrower effects/resources. Evidence checks reject source
  drift; runtime outputs need explicit treatment. Exploratory evidence is provisional
  unless candidate stability and applicable inputs are proven.
- External edits cannot be prevented by Forge's cooperative reservations. Detect
  candidate drift, invalidate affected evidence and reconcile; do not silently
  overwrite human work or accept a moving candidate. Tests/check databases and other
  mutable resources must be scoped or explicitly serialized by resource identity.

Evidence reuse binds candidate contents, relevant generated inputs, command and
policy versions, environment/dependency identity and outcome. Explain why a check
reruns. Conservative invalidation is preferable to claiming dependency-aware reuse
without a defensible input map. Independent worktrees remain usable during every
barrier, check, review and reconciliation above.

Evidence consumers must preserve the controlled tools' actual persisted formats.
Commit callback identity binds the original request digest; its audit arguments
retain only the message digest, with terminal preparation/publication proof
checking both. Named checks reference a receipt whose parent artifacts contain
the command result and bounded output. Handoff and final acceptance verify those
bytes, producer identity and current candidate; the locked application rechecks
the same complete artifact closure. A queued candidate repair may reserve future
attempt budget while holding no provider process or execution-capacity lease.

## Profiles, approvals and operator experience

Use operator-wide versioned profile defaults with optional project overrides.
Resolve and freeze the effective profile for each run; the approved execution
envelope covers its allowed role routes and fallbacks. Default/profile edits
affect future runs, not already-approved routing. Keep route-profile versioning
separate from project safety policy; genuine safety-policy changes still follow
the existing approval/invalidation rules.

Automatic fallback is permitted only within the run's approved set, after previous
effects and ownership are safe. Preserve partial work and pass its verified state
to the successor. A policy rejection is not a reason to bypass the same restriction
through another provider. Distinguish quota exhaustion, login failure, unsupported
model/capability, outage, budget exhaustion and uncertain termination. Record the
reason and effective route. Unavailable primary routes pause for operator action;
they never silently switch to the proposed future Sol primary.

### Durable quota admission

Confirmed usage exhaustion is shared PostgreSQL state keyed by provider and the
applicable non-secret account/quota-pool labels. Route-to-pool configuration is
separate from the frozen model/billing envelope. The default groups a local
provider account across models within its authentication/billing mode; explicitly
map separate accounts and model-specific pools. Each admitted attempt retains its
resolved pool and observation revision, so later configuration changes cannot
misattribute a result. Never read development-framework JSON caches or invoke its
provider scripts from the Forge runtime.

Retain observation time, stable evidence/reason, source attempt or audited operator
report, optional unambiguous reset, and next eligible time. Concurrent observations
cannot shorten an active block. Unknown resets use a configurable bounded probe
cooldown (default 3600 seconds, 60–86400 seconds), explicitly distinguished from a
known reset. Expiry means eligible to attempt one recovery probe, not confirmed
available quota. Preserve historical evidence after recovery; absent allowance
telemetry remains unknown.

The short scheduler/admission transaction is the launch authorization point. Check
the shared pool before creating an attempt, reserving budget or retaining execution
capacity. Scan past blocked pools. A blocked specialist may use an eligible frozen
fallback with the same billing boundary after prior client/effect/ownership
reconciliation; otherwise retain the queued task. Preserve partial files, task/run
identity, cumulative budgets and the selected primary. A real quota-failing attempt
is accounted once; suppressions and quota deferral spend no repair debit.
If the chosen fallback also exhausts, reconsider the frozen preferred binding
when it becomes eligible. A fallback's stopped handoff and retained tool receipts
must remain valid for existing application and acceptance checks under that same
frozen envelope; fallback admission alone does not establish completion.

Only one recovery probe per blocked pool may be admitted across workers. Its
ownership survives restarts and cannot expire while a previous client might still
run. Reuse durable launch/lease recovery evidence and the run lock shared by
renewal and launch intent. Recovery skips a busy run; it must not infer expiry or
an absent client from evidence hidden by an uncommitted renewal or launch.
Already admitted requests may
finish, but a success admitted against an older observation revision cannot clear
newer exhaustion. HTTP 429, short-term throttling, authentication, local session
budgets, outages and unsupported routes are distinct from confirmed account
exhaustion.

Task/status inspection and the local CLI expose blocked/unknown/eligible, reason,
observation/reset or probe time, in-flight probe and selected approved fallback.
Operator exhaustion/reset reports use existing authentication, CSRF, idempotency and
audit transactions; they cannot force quota available, clear a longer active block
or grant a model/billing approval. Controlled-time fake clients and PostgreSQL
concurrency/restart tests establish these guarantees without live provider calls.

## Runtime boundary, billing and recovery

Keep the Forge-owned AgentGateway boundary, evolving AgentRequest/AgentResult as
needed for typed orchestration and honest telemetry. Extract ADK invocation/tool
envelopes into Forge-owned contracts; retain Google ADK as one implementation.
Production workers and live evaluations must use the same request-time runtime
factory, resolving the frozen provider/client/auth route rather than one global
Google gateway. A subscription-only worker must start without an API key or API
pricing catalog. Preserve API-key pricing enforcement for explicitly paid routes.

ControlledToolService remains authoritative. Clients use only its per-attempt
broker: disable built-in reads as well as shell/write/network/subagent tools, and
isolate inherited settings, hooks, plugins and MCP servers that could bypass the
boundary. Authenticate callbacks with authority bound to run, task, attempt,
worktree, role and policy. Never accept caller-selected authority or arbitrary CLI
argv. Use fixed supported launch configurations and official authentication flows;
do not extract/copy OAuth credentials, emulate private endpoints or import the
development framework's bypass flags. Isolate configuration without assuming that
existing sign-in survives relocation: prove supported login/configuration behavior
for each client. Bound/redact streams and handle client transcripts and temporary
files without leaking credentials into Forge artifacts.
