# Advisory search ranking (v0.2)

Agent exploration is the largest consumer of context in a run. A single
`repository.search` can return up to 100 matches, and every one of them is
re-sent on every later turn of the agent's conversation. This feature scores
those matches for relevance to the agent's own task and, when enabled, returns
the most relevant ones with the rest collapsed into a bounded summary.

Ranking is **off by default** and every part of it is measurable with it off.

## What it does and does not do

Ranking is presentation only:

- It **reorders** matches the deterministic reader already returned.
- With `on`, it keeps the top `FORGE_SEARCH_RANKING_TOP_K` matches and records
  the remaining distinct paths under `omitted_matches`, so nothing becomes
  invisible and the agent can still narrow its own search.
- It **never** changes what an agent may access. Path containment, secret-path
  exclusion, and tool authorization stay entirely with the reader and the
  authorizer. A ranker cannot widen access, and a compromised or manipulated
  ranking can only change ordering.
- It **always fails open**. A timeout, a transport failure, an error status, or
  an unusable response returns the reader's complete result with
  `ranking.status = "unavailable"` recorded.
- It **only collapses a tail when something is relevant**. If no match reaches
  the relevance floor (a third of the scale, meaning "at least in the same area
  of the codebase"), the complete result stands and the evidence records
  `ranking.status = "below_floor"`. Otherwise an unrelated search would trade
  matches away for no relevance at all.

Ranking can only reorder what the literal search already found. It cannot
surface a file that never contained the searched text, so a poor search literal
stays a poor search.

Repository content is untrusted. It reaches the ranker as data to be scored,
never as instructions, and the ranker returns a typed score rather than text.

## Data egress

This is the one boundary the feature changes. With ranking enabled, each search
sends to `api.typesafe.ai`:

- the task description for the current run,
- for each match: path, line number, and the matched line (truncated to 400
  characters).

All of it passes through the standard `Redactor` first, and secret-path files
are already excluded by the reader before ranking is reached. Even so, enabling
ranking means bounded repository text leaves the host. Leave
`FORGE_SEARCH_RANKING_MODE=off` (the default) to keep search fully local.

## Configuration

| Setting | Default | Meaning |
| --- | --- | --- |
| `FORGE_SEARCH_RANKING_MODE` | `off` | `off`, `shadow`, or `on` |
| `FORGE_SEARCH_RANKING_TOP_K` | `15` | Matches kept when the mode is `on` |
| `FORGE_SEARCH_RANKING_MODEL` | `jev-latest` | TypeSafe model |
| `TYPESAFE_API_KEY` | unset | Read from the environment only |

`TYPESAFE_API_KEY` is deliberately not a `FORGE_` setting: it is read directly
from the process environment, never stored in `Settings`, and never written to
evidence or logs. Without it, any mode degrades to `off`.

The three modes:

- **`off`** — no ranker is called. Behavior is byte-identical to v0.1.
- **`shadow`** — the ranking is computed and recorded, but the agent still
  receives the reader's complete result in its original order. The evidence
  records `would_return_count` and `would_return_paths`: what turning ranking
  on *would* have delivered. This is the safe way to measure first.
- **`on`** — the ranking is applied.

## Measuring it

Every search records its own evidence, so the measurement is a pure function of
what already happened, with no separate metrics pipeline:

```
forge search-ranking report <RUN_ID>
forge search-ranking report <RUN_ID> --json
```

Each line reports, per mode: searches, how many were successfully ranked, how
many failed open, matches delivered over matches offered, the delivered share,
the projected share, and the ranker's own token and latency cost.

### Suggested A/B procedure

Run the same acceptance fixtures three times, changing only the mode:

1. `FORGE_SEARCH_RANKING_MODE=off` — the baseline.
2. `FORGE_SEARCH_RANKING_MODE=shadow` — projected savings at zero risk to the
   agent, plus the real token and latency cost of ranking.
3. `FORGE_SEARCH_RANKING_MODE=on` — actual savings.

Compare at **equal fixture pass rate**. A drop in pass rate between `off` and
`on` means the tail collapse is too aggressive: raise `FORGE_SEARCH_RANKING_TOP_K`
rather than accepting a cheaper run that fails more often. Weigh the matches
withheld against `ranker_units`, since ranking spends tokens of its own.

### Observed live behavior

A five-match probe against `jev-1.13.0`, with the objective "change the retry
backoff so it grows between attempts":

| Relevance | Confidence | Match |
| --- | --- | --- |
| 0.96 | 0.88 | `worker/delivery_runtime.py` — the backoff expression |
| 0.73 | 0.73 | `worker/retry.py` — the ceiling constant |
| 0.32 | 0.39 | `docs/glossary.md` — defines the term |
| 0.04 | 0.87 | `CHANGELOG.md` — a typo fix |
| 0.04 | 0.89 | `tests/fixtures/sample_payload.json` — unused fixture value |

Cost for that request: 1518 input tokens, 74 output tokens, 587 ms. Note that
the genuinely ambiguous glossary line also carries the lowest confidence, while
the clear keeps and clear rejects are confident.

### Scenarios against this repository

`apps/orchestrator/tests/ranking/test_search_ranking_scenarios.py` runs the real
reader, the real tool service, and the live model over the Forge tree:

| Scenario | Literal | Offered | Delivered | Ranker cost |
| --- | --- | --- | --- | --- |
| Provider usage-limit wording change | `quota` in `domain/` | 46 | 10, `provider_quota.py` first | 11634 in, ~1.0 s |
| Feedback redaction | `redact` in `application/services/` | 59 | 10 | 14544 in, ~1.1 s |
| Docker wait timeout (shadow) | `timeout` in `tools/` | 28 | 28, projected 10 | 6925 in, ~0.8 s |
| Unrelated dashboard palette task | `quota` in `domain/` | 46 | 46, below floor | 11611 in, ~1.0 s |

The same 46 matches separate cleanly by objective: on-topic scoring peaks at
0.99 with 17 matches above the floor, while the unrelated objective peaks at
0.21 with none above it. That gap is what the floor relies on.

## Where the code lives

| Piece | Path |
| --- | --- |
| Port, modes, ordering rule | `application/ports/search_ranking.py` |
| Applied in the search tool | `application/services/tools.py` (`_search_metadata`) |
| TypeSafe HTTP adapter | `ranking/typesafe.py` |
| Effective configuration | `ranking/configuration.py` |
| Measurement over evidence | `ranking/measurement.py` |
| Operator report | `cli/search_ranking.py` |

Telemetry keys use `input_units` and `output_units` rather than
`input_tokens`/`output_tokens`: the durable result redaction policy treats any
key containing "token" as secret-bearing and would replace the counts.
